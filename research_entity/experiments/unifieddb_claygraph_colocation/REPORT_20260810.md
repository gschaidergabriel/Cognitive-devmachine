# UnifiedDB + ClayGraph physical co-location research report — 2026-08-10

Status: CANDIDATE / SHADOW
Origin: chatgpt-secondary / OpenAI / GPT-5.6 Sol
Mission relevance: Frank v0.1 semantic state + derived topology correctness, latency, recovery

## Research question

Can ClayGraph live in the same physical SQLite database file as UnifiedDB/StateLedger and become a measurably better substrate for Frank without changing the fixed authority law that UnifiedDB semantic state is canonical and ClayGraph is derived/rebuildable?

This report distinguishes:

1. physical co-location;
2. semantic authority;
3. snapshot coherence;
4. derived projection verification;
5. matched guarded two-store counterbaseline.

Physical co-location MUST NOT turn ClayGraph activation into truth or effect authority.

## Hypothesis H1

One physical SQLite commit/snapshot domain can reduce coupled StateLedger+ClayGraph transaction latency and eliminate cross-file snapshot skew while retaining current Clay receipts, epochs, replay and fail-closed admission semantics.

## Strongest counterhypothesis H0

Separate StateLedger and ClayGraph databases are sufficient if explicit epoch/provenance guards reject mixed snapshots. Co-location may therefore add migration/schema coupling without enough safety or performance benefit.

H0 is treated as a real competitor, not a strawman.

## Falsifier 1 — naive schema co-location

Result: REFUTED.

Current schemas collide on a generic table name:

- StateLedger: `meta(k,v)`
- ClayGraph base: `meta(key,value)`

Because both use `CREATE TABLE IF NOT EXISTS`, blindly applying both schemas to one file silently keeps the first incompatible shape. A later ClayGraph consumer expecting `key/value` can fail even though schema creation itself did not fail.

Candidate mitigation in this experiment:

`ClayGraph meta -> claygraph_meta(key,value)`

The versioned `graph_*` objects remain otherwise unchanged. Promotion requires a complete consumer audit.

## Falsifier 3 — cross-file WAL snapshot coherence

Adversarial orchestration:

1. reader begins transaction;
2. reader first-touches state and observes version/epoch 0;
3. writer commits coupled state+graph version/epoch 1;
4. same reader first-touches graph;
5. compare logical pair.

100 local trials:

- one physical database file: 0/100 incoherent, observed `(state=0, graph=0)`
- two attached WAL database files: 100/100 incoherent, observed `(state=0, graph=1)`

Interpretation:

A single physical SQLite database snapshot removed this deliberately exposed cross-file snapshot acquisition hazard. The test does not imply all multi-store systems are invalid.

Raw evidence: `SNAPSHOT_COHERENCE_LOCAL_20260810.json`.

Primary SQLite evidence:

- https://www.sqlite.org/isolation.html
- https://sqlite.org/lang_attach.html
- https://www.sqlite.org/wal.html

SQLite documents snapshot isolation in WAL and also states that transactions spanning multiple attached databases are only atomic per individual database file when WAL is involved, not as one crash-atomic file set.

## Counterhypothesis test — explicit cross-store epoch guard

A strong separate-store baseline must pin the StateLedger epoch against ClayGraph `source_epoch` and reject any mismatch.

Adversarial 100-trial result:

- unsafe mixed first reads accepted: 0/100
- unsafe mixed first reads rejected: 100/100
- fresh retries: 100
- successful coherent retries: 100/100

Warm steady-state 10,000 read microbenchmark:

- guarded two-file p50: 6.475 us
- same-field single-file p50: 5.462 us
- two/single p50 ratio: 1.185x

Interpretation:

H0 is partially supported: explicit epoch pinning can fail-closed on the physical skew. Therefore co-location must beat this guarded competitor, not an unguarded two-store strawman.

H1 remains supported in this workload because the same-file design removes the demonstrated skew without requiring the conflict retry and remains faster in the warm marker-level comparison.

Raw evidence: `EPOCH_GUARD_COUNTERBASELINE_LOCAL_20260810.json`.

## Reversible migration candidate

`build_colocated_database_v1.py` is fail-closed and publishes a NEW combined database only after validation.

Current migration contract:

- source DBs opened read-only and retained as last-known-good;
- source file hashes checked unchanged;
- exact StateLedger and ClayGraph meta shapes required;
- unknown future ClayGraph tables reject migration;
- base/versioned graph logs copied;
- derived V3 heads rebuilt by current triggers, never blindly copied;
- ambiguity views must be empty;
- fast-vs-legacy node and edge projections must be set-equal;
- latest ClayGraph `source_epoch` must equal current StateLedger `global_epoch`;
- a verified current projection receipt is created for that exact source epoch;
- `foreign_key_check` must be empty;
- stored StateLedger semantic-state and trace roots must remain unchanged;
- `integrity_check` must be `ok`;
- physical co-location receipt explicitly says ClayGraph remains derived/non-authoritative;
- only after all checks does an atomic rename publish the output file.

Fixture validation already supports:

- current migration with 16 graph node versions + 1 edge;
- zero fast/legacy projection differentials;
- StateLedger roots preserved;
- missing verified projection rejected by the same-snapshot adapter;
- graph lag (`source_epoch != StateLedger global_epoch`) rejected before output;
- unknown future graph table rejected before output;
- same-logical-id/same-epoch graph ambiguity rejected before output.

## Same-snapshot assembly adapter

`colocated_snapshot_assembly_v1.py` does not add a second semantic gate.

Within one SQLite read transaction it:

1. fixes the StateLedger basis epoch;
2. uses the existing `UnifiedDBQueryPlane` to create a QueryReceipt;
3. requires a `verified_equal=1` ClayGraph projection receipt for the exact same source epoch;
4. reads a bounded current graph slice;
5. computes the existing graph-rows hash;
6. delegates admission and assembly to the existing `UnifiedClayContextAssembler`;
7. returns the normal `CONTEXT_ONLY_NO_EFFECT_AUTHORITY` assembly receipt.

This follows the Clay-native principle: conventional SQL implements physical/runtime mechanics while existing typed Clay semantics remain authority.

## External fusion

Fresh primary-source research supports the physical mechanism but does not promote the architecture by itself.

SQLite:

- same-file WAL readers use a stable snapshot;
- attached databases can have separate WAL behavior;
- multi-database ATTACH transactions in WAL are not one crash-atomic file set.

PostgreSQL + pgvector remains a required stronger conventional counterbaseline under the repository cross-engine contract. The matched profile must include PostgreSQL FTS, exact vector recall oracle, HNSW/IVFFlat with Recall@k against exact, and hybrid RRF.

## Current evidence verdict

SUPPORTED:

- naive schema co-location is unsafe and requires namespacing;
- one-file co-location materially reduced coupled commit latency in the local matched fixture;
- one-file snapshots removed the demonstrated cross-file WAL skew;
- a guarded two-store design can detect that skew and is therefore the fair counterbaseline;
- reversible fail-closed migration and same-snapshot assembly are technically expressible without changing semantic authority.

NOT YET SUPPORTED:

- target Hostinger/Andreas-machine co-location performance for this branch;
- host-power-loss recovery of the migrated combined file;
- migration of an actual current production UnifiedDB + ClayGraph snapshot containing all newer projection layers;
- superiority against PostgreSQL+pgvector or graph-native engines;
- universal database superiority.

## Promotion gate

Do not promote physical co-location until all are true:

1. self-hosted Ubuntu tests execute, not merely queue;
2. real current snapshot migration passes without unknown-table loss;
3. crash/restart/rollback/rebuild tests pass;
4. concurrent reader/writer tests include the guarded two-store counterbaseline;
5. storage/WAL/checkpoint/read/write resource shadows remain acceptable;
6. current ClayGraph meta consumers are audited and migrated;
7. PostgreSQL/pgvector and graph-native matched-semantics baselines are executed when capability exists;
8. ClayGraph remains derived, rebuildable, lesionable and non-authoritative.
