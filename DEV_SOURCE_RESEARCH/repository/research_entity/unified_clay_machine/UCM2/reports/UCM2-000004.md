## Question

Can UCM2 reconstruct its bounded semantic materialization exactly from its own event stream after loss/corruption of the materialized tables, and what does such a replay log actually prove about lineage authority?

## Competing realities

### H1 — replay-complete event authority is sufficient for semantic reconstruction

If every material mutation stores its complete reconstruction payload under one monotonic epoch and the stream is integrity checked, a fresh UCM2 or a damaged materialization should be able to reconstruct the same bounded self-read.

### C1 — the existing event log is only an audit hint

The prior v1 `UPSERT`, `LINK` and `EXPERIENCE` events omitted semantic fields needed to reconstruct materialized state. Under this counter-reality, replay cannot be authoritative even if individual event hashes are valid.

### H2 — a hash chain can prove canonical lineage

A chained terminal digest might appear to identify the unique machine history.

### C2 — hash-chain integrity proves only self-consistency

A coherent sibling branch can be altered and fully re-hashed, producing a second internally valid history. Selection of the canonical branch therefore requires an external trusted anchor/admission rule rather than self-hashing alone.

## Primary external evidence

Official SQLite WAL documentation was consulted only to separate storage-engine crash recovery from UCM semantic recovery:

- SQLite WAL commits are represented by commit records appended to the WAL and SQLite can recover the WAL index after a crash.
- WAL recovery verifies frame checksums and stops at the last valid commit frame.

Sources:
- `https://www.sqlite.org/wal.html`
- `https://www.sqlite.org/walformat.html`

This supports a narrow distinction only: SQLite can recover a structurally committed database/WAL state, but UCM2 still needs application-level semantics if it wants to rebuild derived/materialized cognitive state from an event history.
