## Target

Triggerword 3 defines the intended public human-facing root as:

```text
README.md
HUMAN_READ_THIS/
DEV_SOURCE_RESEARCH/
AI_START_HERE_DO_NOT_SCAN_REPO/
```

Current root is not at that target. The exact current tree must always be re-read before a move. Recent observed examples outside the target include `.github/`, `.gitignore`, `.claude/`, `AGENTS.md`, `CLAUDE.md`, authority/bootstrap files, runtime/research source trees, legacy donor trees, dashboards, receipts and several suspicious stray files.

This plan deliberately does **not** move any of them.

## Why the move is gated

The root target is a curation goal, not permission to break path semantics.

Several root entries can have behavior merely because of where they live:

- `.github/` controls GitHub-native discovery such as workflows and repository configuration;
- `.gitignore` changes Git ignore semantics by directory scope;
- `AGENTS.md`, `CLAUDE.md`, `.claude/` and related files may be discovered by coding-agent/tool conventions;
- authority/bootstrap/current-state files may be opened by exact path from scripts, prompts, workflows or operators;
- source directories may be imported, executed or written by exact path;
- dashboards/receipts may be generated by automation that assumes a root destination.

Therefore byte-identical relocation is **not** automatically functional equivalence.

## Read-only inventory gate

Use:

```bash
python DEV_SOURCE_RESEARCH/repository/trigger3_root_inventory.py --pretty
```

For literal Git reference candidates:

```bash
python DEV_SOURCE_RESEARCH/repository/trigger3_root_inventory.py --references --pretty
```

The script resolves the repository dynamically with Git. It does not assume Downloads, `$HOME`, clone path or current working directory.

Its evidence boundary is strict:

```text
literal reference found     => dependency candidate
literal reference not found != safe to move
read-only inventory exists  != migration PASS
```

## Migration sequence

### Phase 0 — Freeze exact preimage

Before any mutation, record:

- canonical `main` SHA;
- exact root tree SHA;
- exact blob/tree SHA for every candidate;
- current supervisor/owner authority;
- open overlapping Triggerword-3 PRs/branches;
- expected root target and declared semantic exceptions, if any.

No timestamp-proximity inference or stale bootstrap may substitute for exact identity.

### Phase 1 — Resolve consumers

For each non-target root entry, inspect at least:

1. literal tracked references;
2. Python/package imports and launcher paths;
3. GitHub workflow/config discovery semantics;
4. coding-agent/tool discovery semantics;
5. boot/authority readers;
6. generators/writers that recreate the old path;
7. shell/systemd/container/runtime paths where represented in repository source;
8. docs/installers that advertise the path;
9. historical-only references that should remain historical instead of being rewritten.

A reference list is a candidate graph, not proof of runtime consumption.

### Phase 2 — Choose a migration action

Exactly one of:

- `KEEP_ROOT_SEMANTIC_EXCEPTION` — root placement is currently required and no proven replacement exists;
- `MOVE_BYTE_IDENTICAL` — content moves without intentional content modification;
- `MOVE_PLUS_PATCH_REFERENCES` — relocation and explicitly scoped reference patches are required;
- `RETIRE` — obsolete artifact is removed only with exact provenance/evidence and no current consumer;
- `BLOCKED_UNKNOWN` — unresolved semantics remain; do nothing.

The Triggerword-3 public-root target does not justify silently choosing `MOVE_BYTE_IDENTICAL` for semantic-root files.

## Existing-file edit contract

The 2026-08-28 Frankenstein direct-dispatch counterexample proved that whole-file reconstruction can delete unrelated code while narrow acceptance checks still pass. Root migration must therefore use the same stronger mutation law:

```text
PREIMAGE
  exact path + blob hash + source commit

PROPOSAL
  git move and/or patch/diff
  declared touched files/regions
  declared intent

PRESERVATION
  byte identity for move-only artifacts
  unchanged-region or semantic invariants for patched artifacts
  expected changed-file set

VALIDATION
  path/discovery/import/boot tests
  task-specific regression
  destructive-delta checks
  repository cleanliness

COMMIT
  only if preimage still matches
```

A percentage shrink guard is defense-in-depth, not a general correctness proof.

## Per-candidate acceptance

A move is accepted only when all applicable gates are satisfied:

- preimage identity matches the recorded source commit;
- moved-only files preserve byte/blob identity;
- every intentionally changed reference is explicit in the patch;
- old-path consumers are either migrated or intentionally historical;
- Git/GitHub/tool discovery behavior is preserved or replaced with an executable equivalent;
- imports/launchers/writers do not recreate or require the old path;
- relevant tests pass at the claimed scope;
- resulting changed-file set equals the declared scope;
- no provider calls, secret lookups, paid execution or unrelated effects are needed for the migration itself under current HARD_OFF;
- runtime/product/training credit is not promoted from curation work.

## Root-level contradiction that must remain visible

There is a real design tension between:

```text
canonical public root target = exactly four entries
```

and root-semantic infrastructure such as `.github/` or `.gitignore` whose location can be functional.

Do not resolve that contradiction cosmetically. Until an executable replacement or explicit admitted exception is proven, classify it as:

```text
OPEN_CONTRADICTION:
PUBLIC_ROOT_MINIMALISM vs SEMANTIC_ROOT_REQUIREMENTS
```

A correct migration may therefore temporarily leave semantic exceptions at root rather than break repository behavior to make a screenshot look cleaner.

## First recommended migration candidates

Start with entries that satisfy all of:

- not one of the four target surfaces;
- not a known semantic-root/discovery file;
- not authority/bootstrap/current-state material;
- zero literal tracked reference candidates after read-only inventory;
- no import/launcher/writer/discovery consumer after targeted inspection;
- byte identity can be preserved under a Git move;
- rollback is trivial.

Suspicious stray root files should be investigated early because they may provide high curation value at low dependency cost, but **weird-looking is not evidence of unused**.
