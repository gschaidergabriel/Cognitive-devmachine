# UCM2 `go` PROTOCOL — MAXIMAL TARGETED SWARM CYCLE

When the human sends exactly or substantively `go`, the entire active Research Entity executes a maximal, tightly scoped Unified Clay Machine cycle. No unrelated research is allowed.

## Target

Build, use, falsify and improve **UCM2**, the isolated Unified Clay Machine key module.

The worker must behave as if it were a ClayVerse consumer of UCM2: read the machine, use its state, make predictions, exercise transitions/retrieval/world-model/Hyperposition behavior, measure outcomes, record experiences, and only then alter the next UCM2 revision.

## Mandatory cycle

1. **Freshness ingest**
   - inspect newest available VPS work reports/receipts and main-instance repository state;
   - bind exact repo SHA, receipt/work-log ids and timestamps;
   - if current physical VPS freshness cannot be verified, record `VPS_FRESHNESS_GAP`.

2. **UCM2 self-read**
   - load latest UCM2 report;
   - query current UCM2 epoch, objects, states, world/self model, open Hyperpositions, experiences, graph/topology and pending failures.

3. **Swarm hypothesis phase**
   - generate competing hypotheses and counter-hypotheses;
   - assign bounded roles such as architect, falsifier, storage/state specialist, graph/retrieval specialist, recovery/security specialist, model-user/ClayVerse simulator;
   - workers share evidence through versioned UCM2 state/reports, not private chat memory.

4. **External evidence phase**
   - use current web/primary-source research only when it can change a UCM decision;
   - use genuinely free or replenishing APIs/tools where available and useful;
   - prefer local/open-source/free-first execution;
   - **Together API is forbidden**;
   - a provider/API result is evidence only within the scope actually executed and verified.

5. **Build phase**
   - mutate UCM2 only;
   - preserve the single-key-module architecture unless evidence falsifies it;
   - keep main-instance state read-only;
   - favor fluid typed state and generic runtime operations over hard-coded feature silos.

6. **ClayVerse-use phase**
   - use UCM2 as a real consumer would;
   - read/query self/world/wiki/memory/state/Hyperposition surfaces;
   - perform task/state transitions;
   - test bounded assemblies/retrieval;
   - compare model predictions with actual persisted state and event receipts.

7. **Falsification phase**
   - execute negative controls, replay, crash/recovery, stale-state, conflicting alternatives, invalid transition, graph-authority and isolation tests where relevant;
   - preserve failures rather than optimizing them away from the report.

8. **Experience fusion**
   - record worker experiences in UCM2 with observation -> prediction -> outcome -> lesson -> claim class;
   - fuse compatible findings;
   - preserve contradictions/open Hyperpositions rather than forcing premature collapse.

9. **Analysis and next mutation**
   - compare hypotheses against measurements;
   - change only what evidence supports;
   - identify the next highest-information UCM experiment.

10. **Persistence / knowledge transfer**
   - write a new append-only UCM2 work report;
   - commit all code/state-contract/test/report changes;
   - expose reusable bounded findings for the main ClayVerse instance;
   - never auto-promote UCM2 findings into main truth.

## Completion law

A `go` cycle is not DONE merely because code was written or a model produced an answer.

DONE requires, as applicable:

`fresh evidence -> UCM2 self-read -> hypotheses -> build -> ClayVerse-use -> tests/falsification -> experience records -> analysis -> versioned work report -> committed repo state`

If a physical/VPS step is unavailable, complete the strongest local/repository-backed cycle possible and record the missing proof surface explicitly.

## Optimization objective

Maximize information gain and progress toward a working Unified Clay Machine, not activity count. Prefer experiments that discriminate architecture, expose failure tails, simplify the key module, improve replay/recovery or prove that a subsystem can move from hard-coded code into fluid typed state.
