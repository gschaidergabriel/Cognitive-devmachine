# ATOMIC — LSCW deep recurrence

Run: `atomic-20260811T2244p0700-chatgpt-secondary-lscw-deep`

## Final classification

**LSCW-001 is REVISED, not promoted.**

The initial broad candidate — one cross-stage semantic-conservation witness spanning source, compiler, artifact, ProductStart, runtime consumption, effects, re-entry and recovery — was too strong. A fresh real ClayCode defect falsified the claim that explicit lifecycle hard fields or a semantic root derived through the same frontend can prove arbitrary language semantic preservation. Unary negation could disappear during parse/lowering while all lifecycle identity/authority fields remained unchanged. The target repair therefore becomes a canonical negative control.

The surviving candidate is **LSCW-R1: Linear Semantic Conservation Witness, hard-field lifecycle form**.

It may be useful only for explicit material lifecycle dimensions such as selected state lineage, artifact subject, installed artifact, actually consumed runtime dependency, effect policy, execution generation, user-intent scope, verified outcome, causal credit, reward utility authority and process lease. Language/compiler semantics remain separately validated by independently grounded source-target behavior/refinement/differential/metamorphic/verified-compiler evidence.

No target Frank code was changed by this ATOMIC run. No effect authority, truth authority, self-Harness authority or training authorization changed.

## Why this slice was selected

The current Frank v0.1 frontier contains multiple individually strong mechanisms but a recurrent composition question:

`Did the exact current successor actually consume the exact admitted predecessor, preserve every material hard field that was not explicitly allowed to change, and avoid stale/sibling/replay lineage?`

The same pattern appears at:

- Clay source/evaluator -> lowered backend;
- build/provenance -> installed ProductStart;
- installed ProductStart -> actual runtime dependency consumption;
- selected semantic state -> boot/recovery;
- effect open -> execution generation/provider outcome;
- verified outcome -> causal credit/re-entry/reward;
- old process -> restarted/recovered process.

Fresh concurrent work made the problem sharper rather than merely speculative:

- ProductStart became an explicit AND-gate over independent evidence axes.
- Build trust was split into trusted producer/policy, cryptographic verification, exact artifact subject, installed bytes and freshness.
- The V4 SQLite path proved a fixed private runtime candidate but still left installed ProductStart/restart composition open.
- A pre-Python PATH/dirname helper hijack demonstrated that a later correct V4 guard does not prove the pre-guard path was safe.
- Compiler capability audit found tautological receipt checks, proving that labels are not measurements.
- ClayCode unary-negation erasure demonstrated real semantic drift below lifecycle hard fields.

## Candidate mechanism after Fusion 2

For a transition with `before` and `after` hard-field projections and a stage rule:

`residual = changed_dimensions(before, after) - stage.allowed_changed_dimensions`

The transition fails closed when `residual` is non-empty, required dimensions are missing, dimension-set/schema identity is stale/unknown, the exact consumed object is not the admitted predecessor, or the predecessor is stale/sibling/replayed.

A candidate linear form consumes one current predecessor witness and issues one successor after validation. This is hypothesized to expose cross-stage replay/chimera cases that ordinary immutable context checks may not expose naturally.

Crucially:

- semantic equivalence != exact product identity;
- exact product identity != effect authority;
- provenance != truth;
- a witness != user intent;
- a witness != provider idempotency;
- a witness != recovery correctness;
- a same-pipeline semantic hash != independent compiler-semantic evidence.

## Synthetic discriminator

A research-only Python reference model used an 18-case frozen corpus: 14 deliberately unsafe mutants and 4 valid transformations.

Results:

- terminal-only proxy: 3/14 unsafe mutants rejected, 4/4 valid accepted;
- local-guards proxy: 7/14 unsafe rejected, 4/4 valid accepted;
- strict artifact hash chain: 12/14 unsafe rejected, but only 3/4 valid accepted because a legitimate semantic-preserving rebuild was rejected;
- LSCW reference: 14/14 unsafe rejected, 4/4 valid accepted.

This result is **not target evidence**. The corpus and candidate are intentionally aligned to test mechanism predictions.

A Python microbenchmark measured the reference witness validator at roughly 8.18 microseconds p50 and 15.46 microseconds p95 per operation, versus about 0.161 microseconds p50 for the small local-field proxy, with a 640-byte JSON witness. These numbers are local Python implementation shadows only, not ClayCode, installed-product or target-VPS costs.

## Ablation results

On an expanded 16-unsafe/5-valid synthetic mutation set:

- remove linear consumption -> replay mutant escapes;
- remove state-lineage dimension -> state swap, recovery sibling and cross-stage chimera escape;
- remove runtime consumed-object binding -> wrong SQLite/runtime object escapes;
- remove effect-policy dimension -> stale/wrong effect-policy outcome escapes;
- remove dimension-set/schema currentness -> unknown schema dimension escapes;
- allow unknown dimensions -> unknown/missing material dimensions can pass;
- strict hash chain -> false rejects legitimate semantic-preserving transitions and still misses semantic authority/policy/reward cases;
- stronger conventional `CurrentExecutionContext` proxy -> accepts all valid cases and misses only the explicit cross-stage replay/other-epoch/chimera cases in the synthetic model.

That last baseline is the main threat to LSCW-R1.

## Real kill test: unary-negation semantic erasure

Fresh target evidence showed that an anonymous `!` token could disappear in the parser and a conditional grammar rule could inline the remaining operand, changing `!a` into `a` before AST lowering. The repaired candidate passed 8/8 focused operator regressions and 200,576 `decide_effect` comparisons with zero mismatches on the accepted target lane.

This kills the broad LSCW claim because a lifecycle hard-field witness can remain unchanged while source semantics are wrong. Worse, a semantic root derived from the same buggy parser may consistently hash the wrong meaning and therefore provide circular confidence.

Revised law:

**Every semantic-changing compiler/lowering stage requires an independently grounded stage validator. LSCW-R1 may bind the validator identity/result, but may not replace it.**

## Late real-world composition evidence

Two fresh deltas independently support consume-bound reasoning:

1. Build-provenance subject swap: validating signer/workflow but not the exact artifact subject lets a different artifact pass; exact subject binding is non-substitutable.
2. Pre-V4 PATH helper hijack: hostile inherited PATH can execute a shadowed helper before `/usr/bin/python3 -I -S` and the V4 guard begin; a correct later guard does not prove earlier consumed execution was safe.

These support exact consumed-object binding as a real requirement. They do **not** prove that LSCW is the best implementation.

## Strongest counterhypothesis result

**NOT DEFEATED.**

The current architecture is converging rapidly toward a simpler equivalent:

- ProductStart is conjunctive;
- build trust has exact subject and installed-byte axes;
- state lineage and execution generations have dedicated mechanisms;
- compiler semantics are receiving direct differential/capability checks;
- storage has explicit runtime admission;
- recovery has dedicated selected-lineage requirements.

Therefore a universal persisted cross-stage witness may merely duplicate these contracts and increase the trusted computing base, persistence amplification and recovery complexity.

## Kill/promote rule

Kill LSCW as production architecture if M1 matches every M2 safety rejection and valid acceptance on real target episodes with lower code/latency/RAM/persistence/TCB cost.

Retain only as test notation if its residual model improves mutation coverage/diagnosis but not runtime behavior.

Promote only if M2 uniquely catches a material real cross-stage substitution/replay/chimera that M1 misses, accepts all valid transformations, survives crash/restart/recovery, and remains resource-competitive.
