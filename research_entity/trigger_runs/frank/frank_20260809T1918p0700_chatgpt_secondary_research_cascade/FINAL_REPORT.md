## 4. External research — evidence classes kept separate

The run checked current primary/official sources and research literature for mechanism feasibility and counterexamples. None is treated as FRANK-specific proof.

### Local 4B

Official Qwen material establishes that the current Qwen3-4B family is a real dense 4B-class local model with long-context support and standard local inference paths. This supports feasibility of the local-model slot, not the claim that it meets FRANK latency, memory, robustness or cognition requirements on Andreas' Ubuntu host. Those remain benchmark questions.

### Persistent state and one logical DB

Official SQLite isolation/WAL semantics show a useful local mechanism shape: concurrent readers, serialized writes, snapshots and explicit checkpoint behavior. The same source also exposes the risks FRANK must test: one-writer contention, long-reader/checkpoint interactions and stale/busy snapshot behavior. This is evidence for testing one local logical DB, not an argument that all physical storage must be forced into one file.

### Capability/FFI boundary

Current WebAssembly component/WASI material reinforces default-deny resource provisioning and typed import/export contracts as useful design precedents. At the same time, WASI 0.3 native-async toolchain maturity is not yet a good reason to hard-lock Frank v0.1 to that runtime. The transferable idea is typed/resource-explicit interfaces; a direct Ubuntu native ABI remains a valid baseline.

### Workspace and memory

Global-workspace literature supports competition/broadcast as a plausible coordination mechanism family, but does not establish FRANK's causal architecture. Recent persistent-memory benchmarks continue to show that retrieval, long-range event relationships, selective forgetting and test-time memory remain difficult even for strong models. That strengthens the engineering rationale for `rich persistent state != current model-facing context` and for a bounded ActiveAssembly, while still requiring a direct FRANK baseline against broad retrieval/context injection.

10. **Normal-code-first H1 vs direct ClayCode-first:** H1 may reduce architecture/compiler confounding; duplicate implementations may create more drift than information gain.

A conventional persistent event-driven system with bounded retrieval and a deterministic capability gateway remains the required null baseline. It must not be weakened merely to favor the FRANK-specific mechanisms.
