## 0. Meaning

Exact `go` continues the whole Clay research/build organism for the **maximum useful synchronous depth available inside the current invocation, tool, capability, context and authority budget**.

GO is not a short continuation command. It is the whole-system recursive controller for:

- current-state assimilation;
- swarm self-coordination;
- broad live external research;
- hypothesis/counterhypothesis generation;
- architecture reasoning;
- implementation and repair;
- executable validation;
- exact measurement;
- cross-branch fusion;
- work reprioritization;
- q23 bidirectional exchange;
- swarm-performance evaluation and self-improvement;
- durable handoff.

Compact law:

`refresh exact current state`
` -> measure swarm + work frontier`
` -> broad fresh external source ecology`
` -> deepen highest-information source/mechanism network`
` -> hypotheses + strongest counterhypotheses`
` -> choose/build/test/falsify`
` -> exact receipts + metadata`
` -> dense evidence fusion`
` -> architecture/test/work deltas`
` -> targeted/pullable swarm reentry + q23 exchange`
` -> measure whether coordination itself worked`
` -> adapt routing/worker/source strategy`
` -> refresh again`
` -> recurse`

Long means **deep, productive and evidence-accumulating**. It never means blind looping, repeated summaries or filler.

## 1. Maximum useful reasoning and visible-output law

Exact `go` deliberately prefers the deepest useful research/build/test path and the most comprehensive useful visible report available in the invocation.

Required behavior:

1. do not stop because one plausible explanation or implementation has been found;
2. continue through countermechanisms, failure modes, executable evidence and cross-branch implications while marginal value remains positive;
3. use available context/output capacity for **new evidence, comparisons, measurements, deltas, unresolved contradictions and reproducible handoff**, not repetition;
4. preserve reproducible decision/evidence traces, never hidden chain-of-thought;
5. final visible GO output should be long when there is material content to report and include all important deltas rather than collapsing the run to a tiny summary;
6. if the platform/tool budget prevents exhaustive continuation, persist the exact frontier so the next `go` resumes from evidence rather than reconstructing from chat.

`MAX_OUTPUT_DEPTH != RAW_TOKEN_BURN`.

Repeated wording, redundant source summaries, duplicated branch messages or untestable speculation do not count as useful depth.

## 2. Mandatory live source-ecology research

Every exact `go` invocation MUST perform fresh external research unless external connectivity is unavailable. A long GO invocation refreshes external knowledge repeatedly, not only once.

### 2.1 Source ecology

For each major GO run, sample the relevant available source ecology before narrowing:

- **official/current:** runtime source, model/library repositories, official docs, standards, provider/API surfaces, release notes;
- **primary research:** arXiv/preprints, original papers, datasets, benchmark papers;
- **peer-reviewed/publisher:** current journal and conference publisher records when relevant;
- **implementation ecology:** GitHub/open-source projects, related agent/research systems, reference implementations and reproducible artifacts;
- **failure ecology:** issue trackers, changelogs, bug reports, negative results, known failure modes;
- **independent evidence:** replications, matched benchmarks and competing implementations when materially useful.

Do not search every class mechanically when irrelevant. But exact GO must deliberately avoid a single-source monoculture and must look outside the Clay project for better mechanisms/counterevidence.

### 2.2 Recursive network deepening

The first search result is a starting node, not the research result.

For every high-value material finding, follow useful edges where expected information gain is positive:

- references/citations;
- source code/functions/APIs;
- benchmark/dataset lineage;
- model/config/runtime implementation;
- newer/superseding versions;
- competing projects;
- known failure reports;
- papers cited by the mechanism;
- projects citing/implementing the mechanism;
- counterhypotheses and null results.

After every material direction-changing external finding:

`fuse -> recompute questions -> perform another fresh retrieval checkpoint`.

One web search at run start is **never sufficient** for a material long GO run.

### 2.3 External research progress requirement

A major external-research phase must produce at least one of:

- genuinely new evidence;
- new counterevidence;
- a newer/superseding implementation fact;
- a new competing mechanism;
- a new falsifier/test;
- a quantified uncertainty reduction;
- an evidence-backed `NO_MATERIAL_CHANGE` after deliberate route changes.

If searches repeat the same ancestry without progress, change query family, source class, abstraction level or competing mechanism.

## 6. Swarm communication protocol v2: questions, beacons, pulls and acknowledgements

Material communication is not only push-based result broadcast.

Supported semantic message classes:

### `KnowledgeNeed`
A worker publishes the exact missing fact/mechanism/test/result that would change its next decision.

### `DiscoveryBeacon`
A compact notice that a new potentially relevant external/internal finding exists. Contains topic tags, provenance, freshness and payload reference.

### `MaterialDelta`
A provenance-bound claim/hypothesis/work/architecture/test/negative-result delta.

### `CounterChallenge`
An explicit request for the strongest evidence against a material claim or architecture candidate.

### `PullRequest`
A receiver requests the full payload or task-conditioned subgraph after a digest indicates relevance.

### `ReentryAck`
Tracks separate states:

`delivered -> reconstructed -> plan_revalidated -> used -> local_effect`.

Delivery is not use. Use is not effect. Effect is not causal credit.

### `SaturationNotice`
A worker reports a locally saturated route only after recording source classes/queries/mechanisms/countermechanisms already attempted.

A SaturationNotice creates a route-change opportunity for other workers rather than silently ending the topic.

## 7. Adaptive communication topology

GO v2 chooses among route modes dynamically:

`TARGETED_FULL_REF`
`TARGETED_DIGEST`
`SUBSCRIPTION_PULL`
`DENSE_FANOUT`
`ANTI_ENTROPY_REPAIR`
`INDEX_ONLY`.

Route selection considers:

- semantic and causal dependency span;
- explicit affected work/claims;
- high-impact invalidation urgency;
- branch subscriptions/KnowledgeNeeds;
- current branch load;
- payload size;
- source/provenance ancestry;
- stale/projection risk;
- predicted reconstruction/repair cost;
- observer/control-plane resource cost.

Rules:

- ordinary local deltas prefer targeted digest/ref + pull;
- dense/global invalidations may use dense fanout if safer/cheaper;
- low-relevance material stays indexed/pullable;
- route uncertainty is explicit;
- missing predecessor/projection mismatch triggers repair;
- same-file hot observer/control designs are not preferred merely for lower conceptual latency; measured backaction matters;
- routing policy remains benchmarkable and rollbackable.

## 16. Mandatory out-of-the-box experiment

Every exact `go` macro-run attempts **exactly one materially novel, bounded out-of-the-box experiment** outside the current local optimum.

It may be cross-domain, first-principles or Clay-native, but must be:

- reversible;
- lesionable;
- baseline-controlled;
- rollback-defined;
- measured;
- explicit about whether it touches historical organ functions;
- compatible with GWT/Frank authority invariants;
- allowed to return `NO BENEFIT` or `REFUTED`.

Do not multiply out-of-box experiments just to increase novelty count. GO's additional depth should come primarily from deeper evidence/falsification/build loops.

- alter route mode;

- change external source mix;

## 22. GO v2 falsification requirements

GO v2 itself must be measured against the prior protocol/current mesh.

Strong counterhypotheses:

- telemetry/profile/ack overhead dominates progress gains;
- worker history creates lock-in and reduces exploration;
- selective memory misses relevant private findings;
- adaptive topology adds complexity with no real-repo benefit;
- mandatory broad live research creates noise instead of decisions;
- q23 coupling captures global priority without executable value;
- longer visible output reduces usability/reproducibility instead of improving it.

Use replay/fault tests and resource accounting. Do not promote stronger networking simply because it appears more sophisticated.
