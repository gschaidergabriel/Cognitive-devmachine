# 2. Successor effect-state law

Frankenstein 2.0 shall use one deterministic effect authority with distinct causal state objects. Never collapse the following into one boolean/status:

```text
EffectRequest
 -> AdmissionDecision
 -> EnforcementReceipt
 -> ExecutionReceipt
 -> WorldEffectVerification
 -> ResultReentry
 -> CompletionEvidence
```

Minimum identities carried end-to-end:

```text
tool_use_id or generated invocation_id
session_id
agent_id
task_id
turn_id
causal_id
generation
request_digest
capability/effect scope
```

`session_id` is context, not invocation identity.

## 2.1 EffectRequest

Represents a candidate external or state-changing operation before authority is granted.

Required properties:

- immutable invocation identity;
- exact requested tool/action + normalized arguments digest;
- originating Goal/Task/Turn/Cognitive-cycle refs;
- source generation;
- declared effect class/scope;
- parent response/candidate identity where generated by Voice/LLM cognition.

## 2.2 AdmissionDecision

Typed state:

```text
ALLOW
DENY
UNKNOWN
```

This is a policy decision, not evidence that execution happened.

A denied request must never later become successful merely because a matching PostToolUse-like event appears.

## 2.3 EnforcementReceipt

This proves that the real executor/host boundary actually honored the decision.

For DENY:

```text
DENY => zero dispatch / zero effect submission
```

For ALLOW:

```text
only the exact admitted request identity may be submitted
```

Bookkeeping such as historical/current `ABGELEHNT` rows without actual blocking does not earn enforcement credit.

## 2.4 ExecutionReceipt

Execution receipt proves bounded tool/process execution facts only.

Bind at least:

- invocation/request identity;
- exact executable/tool identity;
- command/argument digest where relevant;
- source SHA/generation where relevant;
- execution environment identity;
- exit/result status;
- bounded output/result digest;
- timestamp/monotonic sequence.

A string such as `test:0:description` is not sufficient completion evidence without an immutable runner receipt.

## 2.5 WorldEffectVerification

Execution success is not equivalent to success in the external world.

Typed state:

```text
SUCCEEDED
FAILED
UNKNOWN
```

Examples:

- file edit: resulting exact bytes/hash may verify the effect;
- network/external action: successful local submission may still leave world effect UNKNOWN;
- visual/physical action: post-action Retina/VisualNeed may be appropriate verification;
- tool transport failure after possible submission must not be assumed cancelled.

## 2.6 ResultReentry

Observed result is re-entered into UnifiedDB/Agency/Grid state with its exact invocation/task/causal lineage.

Result re-entry does not by itself imply Goal completion.

## 2.7 CompletionEvidence

Only explicit admissible receipt classes may close work.

Fail closed for:

```text
DENIED
FAILED
UNCHECKED / UNGEPRUEFT
UNKNOWN world outcome
stale generation
wrong invocation
wrong task/turn
unresolved duplicate
unbound textual test claim
missing provenance
```

The CompletionGate uses an allowlist, never `status != some legacy failure string`.
