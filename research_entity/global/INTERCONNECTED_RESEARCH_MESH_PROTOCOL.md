# RAE Interconnected Research Mesh Protocol

## Core rule

No reserved research trigger is an isolated research silo. Every trigger run MUST begin from the current cross-trigger research mesh and MUST return its durable deltas to that mesh.

The connected research branches are:

- `clay` — integrated Synthetic Clay foundry / master synthesis
- `frank` — FRANK whole-system cognitive/runtime architecture
- `gwt` — Global Workspace mechanisms and causal closure
- `emergenz` — emergence measurement and intervention
- `claycode` — semantic IR / internal language / self-representation
- `hyperposition` — contextual alternatives, higher-order codependencies and dynamic topology

`dump` is an intake/fusion command rather than a peer scientific branch, but its promoted outputs enter the same mesh.

The FRANK↔ClayCode feedback edge additionally uses `research_entity/global/GOODMAN_ANTI_ECHO_PROTOCOL.md` so recursive agreement cannot manufacture evidential confidence.

## Mandatory preflight

Before Fusion 1, every research trigger MUST:

1. identify the newest material from every connected branch, including fresh/in-progress artifacts when they are newer than the latest final report;
2. load the branch's relevant final reports, hypotheses, experiments, negative results, architecture deltas, Topic Packets and micro-packets;
3. preserve evidence status and provenance — synthetic/proxy evidence never becomes live evidence merely because another branch reused it;
4. identify cross-branch dependencies, contradictions, duplicate hypotheses, equivalent mechanisms and unresolved interfaces;
5. materialize an `INTERCONNECT_MANIFEST.json` in the new trigger run;
6. cite the interconnect manifest in the run manifest/final report.

A run that omits this preflight is incomplete and cannot strongly promote architecture/scientific claims.

## Branch dependency priorities

All branches ingest all other branches, but attention is weighted by mechanism relevance:

### `clay`
Clay is the integrated master foundry. It must jointly fuse all branches and is responsible for detecting incompatible local optimizations between them.

### `frank`
Clay is the primary scientific/architectural foundation. ClayCode is the primary architecture representation and implementation IR for the next FRANK architecture.

FRANK MUST therefore:

1. start from the newest Clay architecture candidate/research delta;
2. deeply ingest the newest ClayCode completed and in-progress research, including semantic-IR, transition-closure, freshness, dependency/effect derivation, projection, authority and self-hosting results;
3. then integrate GWT, Hyperposition and Emergence constraints plus current FRANK runtime/code evidence;
4. express the resulting architecture as ClayCode semantic IR, not merely as prose or an unrelated implementation-language diagram.

A FRANK architecture proposal that ignores a newer Clay or ClayCode delta is invalid unless it explicitly explains why that result is inapplicable or superseded.

Priority order: `clay -> claycode -> gwt -> hyperposition -> emergenz -> frank history`.

The required architecture source artifact is `FRANK_ARCHITECTURE.claycode.json`. Until ClayCode's final surface syntax is stabilized, this file is a deterministic JSON projection of the meaning-bearing ClayCode semantic IR. Human-readable Markdown and implementation-language code are projections/targets derived from that IR, not the semantic source of truth.

The ClayCode architecture must describe at least stable module/organ identities, state contracts, transitions/operations, dependencies, invariants, GWT/assembly links where applicable, proposal class (`PURE_TRANSFORM | STATE_PROPOSAL | EFFECT_PROPOSAL`), provenance/causal linkage and authority/effect boundaries.

Not every physical byte of FRANK must be self-hosted. The minimal deterministic parser/validator/canonicalizer/bootstrap kernel and external capability/effect authority remain explicitly outside model self-authorization. ClayCode may represent/reference these boundaries but cannot mint their authority.

### `gwt`
Must use Clay system constraints, FRANK runtime realities, Emergence causal tests, Hyperposition/context structure and ClayCode representation/receipt semantics.

### `emergenz`
Must use Clay architecture, GWT intervention surfaces, Hyperposition higher-order structure, FRANK runtime observability and ClayCode causal/provenance representations.

### `claycode`
ClayCode is both a research branch and the architecture language of FRANK. It therefore treats the newest FRANK architecture/runtime research as its primary target-feedback input, while Clay supplies the broader integrated scientific constraints.

Priority order: `frank -> clay -> gwt -> hyperposition -> emergenz -> claycode history`.

Every ClayCode run MUST:

1. load the newest FRANK completed and in-progress research;
2. load the latest available `FRANK_ARCHITECTURE.claycode.json` and `CLAYCODE_ARCHITECTURE_MAPPING.md` when present;
3. identify FRANK-derived assumptions that materially affect ClayCode semantics/runtime;
4. apply the Goodman Anti-Echo Protocol to those assumptions;
5. classify each relevant assumption as `SUPPORTED`, `REFINED`, `REFUTED` or `UNRESOLVED`;
6. materialize `FRANK_CLAYCODE_GOODMAN_REVIEW.json`;
7. integrate only the supported/refined form, preserve refutations as negative/supersession evidence, and keep unresolved assumptions explicitly open;
8. write the resulting ClayCode delta back to the mesh for the next FRANK run.

Circular agreement adds no independent support. `ClayCode -> FRANK -> ClayCode`, or any descendant chain with shared source/experiment ancestry, is one evidence family unless genuinely new independent evidence or a new discriminating experiment enters the loop.

If the latest completed FRANK run predates the architecture-artifact requirement and no `FRANK_ARCHITECTURE.claycode.json` exists yet, ClayCode must explicitly record that absence and use the newest FRANK report/contract as provisional requirements; it must never fabricate the missing artifact.

ClayCode must also use GWT receipt/re-entry semantics, Hyperposition conflict/unknown representation and Emergence observability requirements as independent cross-constraints.

### `hyperposition`
Must use Clay state semantics, FRANK runtime/dataflow constraints, ClayCode representational forms, GWT activation/workspace behavior and Emergence higher-order causal tests.

## Cross-branch contradiction gate

Before final synthesis, every run MUST scan for:

- a new result that contradicts an active hypothesis in another branch;
- a local optimization that worsens a metric another branch treats as a hard constraint;
- duplicated concepts with different names;
- identical concepts with incompatible evidence status;
- a representation claim being mistaken for a mechanism claim;
- an architecture claim depending on synthetic evidence as though it were live evidence;
- stale branch conclusions superseded by a newer run;
- apparent multi-branch agreement that collapses to the same evidence ancestry.

Contradictions are retained, not silently averaged away. The final report must state whether each relevant conflict was resolved, narrowed or left open.

## Mesh write-back

Every durable branch result should carry:

- originating trigger/run;
- affected branches;
- evidence class/status;
- upstream dependencies;
- evidence ancestry/family where cross-branch reuse is involved;
- contradictions or supersessions;
- downstream architecture/experiment implications.

Create cross-links in Topic Packets/micro-packets where practical. A branch-specific result may remain local in confidence, but it must remain discoverable by the other branches.

## Scientific boundaries

Interconnection increases information flow, not evidence strength. Repetition across branches by the same underlying source/experiment is not independent replication. Shared ancestry must be tracked so apparent multi-branch agreement is not double-counted.

The mesh never permits GWT, emergence, self-reference or architectural sophistication to be treated as evidence of phenomenal consciousness without separate justified evidence.
