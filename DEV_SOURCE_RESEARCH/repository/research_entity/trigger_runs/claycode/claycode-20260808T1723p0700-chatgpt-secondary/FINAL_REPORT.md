## Executive synthesis

CC8 established a strong rule: trusted semantics derive a conservative static dependency/effect envelope, complete runtime interposition observes the path actually taken, and `observed_trace ⊆ static_envelope` must hold before selective validation/commit.

CC9 finds that two additional problems become unavoidable once this architecture is connected to current FRANK and ClayGraph:

1. **Basis is multidimensional.** A transition can depend simultaneously on exact state, a CognitiveFrame, a ClayGraph semantic epoch, an activation epoch, a projection dictionary/schema, an operation-semantics version and external capability state. Independently reading the `latest` member of each family can construct a combination that never formed a valid causal basis.
2. **Closure is compositional and identity-sensitive.** A root operation's direct effects are insufficient when it calls helpers, selects callbacks dynamically, reaches the same underlying resource through aliases, or crosses reflection/FFI/plugin boundaries.

The OPEN CC9 candidate is:

# CC-RC1.4 — Certified Basis & Compositional Closure (CBCC)

```text
canonical semantic operation + args
        ↓
trusted op semantics / version
        ↓
operation-specific CAUSAL BASIS REQUIREMENTS
{state_root, frame, graph_epoch, activation_epoch,
 projection_semantics, volatile epochs, ... only if required}
        ↓
COMPOSITIONAL STATIC CLOSURE
primitive summaries
+ transitive callees
+ finite dynamic-target union
+ canonical resource identities
+ predicate / invariant / volatile / capability witnesses
        ↓
unknown reflection / FFI / plugin target set ?
        ├─ yes -> TOP / broaden / isolate / reject
        └─ no
        ↓
state-aware Gamma / deterministic projection compiler
        ↓
projection receipt
{semantic_hash, projection_schema_hash, projection_hash}
        ↓
execution under complete interposition
        ↓
observed trace ⊆ static closure ?
        ├─ no -> fault / widen / reject
        └─ yes
        ↓
typed basis compatibility + invariant + capability checks
        ↓
internal commit OR durable effect intent
        ↓
external capability gateway / idempotent release
        ↓
effect receipt -> outcome -> re-entry
```

The critical refinement is that **a basis certificate is not a universal vector lock**. Each operation's trusted semantics specify which dimensions matter and the compatibility rule for each. Unrelated epoch churn must not invalidate an operation merely because some global version changed.

## 4. External research synthesis

### Effect typing and composition

Koka v3 documents that function types track effects and that effect handlers compose. This independently supports the general ClayCode idea that a function/operation summary should carry what it may do instead of treating side effects as comments.

Current Exa discovery also returned work reconciling effects and capabilities, strengthening the separation between *what can happen* and *which external resource/authority makes it legal*.

### Alias/reachability analysis

Current LLVM Alias Analysis documentation distinguishes `MustAlias`, `MayAlias`, and `NoAlias` reasoning and warns that analysis information must remain synchronized with program transformations. This matches CC9's negative result: identity/alias knowledge is part of the trusted analysis state, not decorative metadata.

Flowistry/ownership-based modular information-flow work gives a useful counterpressure: practical modular analyses can be sound but imprecise, and unsafe/interior-mutability boundaries can lose the annotations an analysis needs. ClayCode should therefore treat unsafe/FFI/plugin gaps as incomplete closure, not invent precision.

### Snapshot and causal metadata

Distributed causal-consistency work uses explicit causal metadata such as vector timestamps when independently stored pieces must preserve causal order. Concurrent snapshot research separately demonstrates snapshot handles that let later operations read multiple locations as of one captured state.

**Transfer:** a ClayCode basis witness can use whichever deterministic primitive the storage/runtime actually guarantees — a true atomic snapshot handle is preferable to a synthetic tuple when available. CC9 does not mandate vectors if the substrate already supplies a stronger atomic snapshot.

### Capability / host boundary

The WebAssembly Component Model explicitly separates component computation from functionality supplied by the host/platform. That continues to be a useful implementation analogue for ClayCode's external gateway and opaque resource handles.

### Proof-carrying actions

2026 `Proof-Carrying Agent Actions` proposes portable action certificates with explicit pre-action admissibility/approval/outcome checkpoints across heterogeneous runtimes. It is not direct proof of CC-RC1.4, but independently converges on the principle that action authority and evidence should travel in a verifier-checkable runtime envelope rather than model prose.

## 5. CC-RC1.4 semantic contract

### A. Snapshot identity remains

Keep:
- `state_root` / semantic snapshot hash;
- provenance / causal episode identity;
- `op_semantics_hash`.

Do not reinterpret `state_root` as the sole freshness/compatibility rule.

### B. Add typed basis requirements

Illustrative semantic form:

```text
basis_requirements = [
  {kind: frame, name: cognitive, policy: EXACT, expected: f9},
  {kind: graph, name: semantic, policy: EXACT|LINEAGE|VALID_AT, expected: g12},
  {kind: activation, name: latent, policy: EXACT|COMPATIBLE, expected: a31},
  {kind: projection_schema, name: workspace_word, expected: ps7}
]
```

The trusted operation registry/compiler defines these. The model may inspect them but cannot remove a required dimension.

### C. Closure composes through the operation graph

A trusted operation summary contains:
- direct resources;
- predicates/ranges;
- invariants;
- volatile/temporal inputs;
- required capabilities;
- static callees;
- complete finite dynamic-target set **or** `unknown`;
- semantics hash/version.

The compiler takes the transitive fixed point over these summaries.

### D. Canonicalize authority-relevant resource identity

Model-facing names are references, not necessarily conflict identities. Normalize where possible:
- DB logical name -> canonical table/key/range identity;
- file/symlink -> policy-approved canonical object identity;
- URL/tool alias -> provider/account/capability resource identity;
- graph relation projection -> canonical relation-instance/epoch identity.

If normalization is ambiguous or unsafe, widen/escalate.

### E. Projection has its own receipt

At minimum:
- `semantic_hash` — meaning-bearing canonical object;
- `projection_schema_hash` — positional dictionary / rendering semantics;
- `projection_hash` — exact transported bytes/tokens where needed.

GWT transport receipt and model uptake may reference this receipt. A valid transport hash does not prove correct semantic projection.

### F. Small-model role

For high-stakes authority/freshness semantics:
- deterministic kernel computes validity/decision or bounded candidate set;
- small model receives a compact certified projection;
- model may reason over non-authority content;
- gateway checks actual authority/effect release independently.

### G. Unknown stays first-class

Reflection, runtime code generation, unknown plugin callbacks or unanalyzed FFI do not become `PURE` because the compiler lacks information. They become incomplete closure and trigger a predeclared broaden/isolate/reject path.

## 6. ClayGraph findings that changed ClayCode

This section is mandatory because ClayGraph is now a deep ClayCode substrate input.

### Changed ClayCode

1. **Basis becomes explicitly multi-epoch.** `graph_epoch_id`, `activation_epoch_id`, and `basis_frame_id` expose that a single snapshot root cannot express every cross-subsystem compatibility requirement.
2. **Activation is typed separately from semantic truth.** ClayCode needs distinct semantic classes for graph truth/evidence state versus latent activation/assembly state.
3. **Assembly needs a reconstructible basis receipt.** A bounded Assembly should reference graph epoch + activation epoch + frame/basis and exact anchor refs so downstream model/GWT use can be audited.
4. **Graph mutation/evolution participates in op semantics.** A migration or schema/dialect change must update relevant semantics/projection hashes and invalidate only operations whose basis/closure depends on it.

### Supported ClayGraph assumptions

- immutable/replayable semantic epochs are a good exact anchor candidate;
- latent activation may be mutable/fast without becoming canonical truth;
- bounded Assembly can be a reader projection rather than the database itself;
- exact anchor validation before high-stakes use is consistent with CC8/CC9.

### Challenged ClayGraph assumptions / requirements back to ClayGraph

- Do not expose only bare epoch integers; include lineage/semantic identity sufficient to reject same-number/different-lineage ambiguity.
- Do not imply that every Assembly requires exact equality of every epoch; emit the operation/query-specific compatibility requirements or enough metadata for ClayCode to derive them.
- Any activation-driven graph escalation must remain a retrieval/selection proposal, not a capability/effect authorization.
- Projection/dictionary version must be receipted if a compact Assembly representation can change meaning across versions.
