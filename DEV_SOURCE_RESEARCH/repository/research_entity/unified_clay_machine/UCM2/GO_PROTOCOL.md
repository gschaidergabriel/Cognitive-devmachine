# UCM2 `go` PROTOCOL — MAXIMAL TARGETED SWARM CYCLE

When the human sends exactly or substantively `go`, the entire active Research Entity executes a maximal, tightly scoped Unified Clay Machine cycle. No unrelated research is allowed.

## Target

Build, use, falsify and improve **UCM2**, the isolated Unified Clay Machine key module.

The worker must behave as if it were a ClayVerse consumer of UCM2: read the machine, use its state, make predictions, exercise transitions/retrieval/world-model/Hyperposition behavior, measure outcomes, record experiences, and only then alter the next UCM2 revision.

## Mandatory cycle

1. **Freshness ingest**
   - inspect newest available VPS work reports/receipts and main-instance repository state;
   - bind exact repo SHA, receipt/work-log ids and timestamps;
   - if current physical VPS freshness cannot be verified, record `VPS_FRESHNESS_GAP`.

2. **UCM2 self-read**
   - load latest UCM2 report;
   - query current UCM2 epoch, objects, states, world/self model, open Hyperpositions, experiences, graph/topology and pending failures.

3. **Swarm hypothesis phase**
   - generate competing hypotheses and counter-hypotheses;
   - assign bounded roles such as architect, falsifier, storage/state specialist, graph/retrieval specialist, recovery/security specialist, model-user/ClayVerse simulator;
   - workers share evidence through versioned UCM2 state/reports, not private chat memory.

4. **External evidence + FREE API organ phase**
   - use current web/primary-source research whenever it can change a UCM decision;
   - use genuinely free or replenishing APIs/tools as first-class temporary research/build/test organs wherever useful;
   - free APIs may be used for research, literature/source discovery, coding, generation, embeddings, reranking, retrieval, VLM/perception, OCR, speech, reasoning, evaluation, synthetic fixtures, adversarial tests, model comparison, data transformation, simulation and any other UCM2-supporting task that remains within provider terms and project safety/authority boundaries;
   - NVIDIA APIs/NIM endpoints are explicitly allowed and should be evaluated for deep cognitive integration where their current free/developer access is actually available;
   - other suitable free APIs may be used opportunistically and compared against local/open-source baselines;
   - **Together API is forbidden**;
   - no paid fallback may silently activate; trial-only credits are not treated as stable free capacity;
   - raw credentials/secrets never enter reports, commits, UnifiedDB or prompts sent to unrelated providers;
   - every material provider/API result records provider/model/endpoint identity, timestamp/freshness, role, input class, result/receipt and failure/limit state where observable;
   - provider output is an observation/candidate, never truth or effect authority by itself.

5. **Build phase**
   - mutate UCM2 only;
   - preserve the single-key-module architecture unless evidence falsifies it;
   - keep main-instance state read-only;
   - favor fluid typed state and generic runtime operations over hard-coded feature silos;
   - free APIs may directly assist implementation, code review, fixture generation, schema design, migration generation or test construction, but produced changes must still be locally/repository tested.

6. **ClayVerse-use phase**
   - use UCM2 as a real consumer would;
   - read/query self/world/wiki/memory/state/Hyperposition surfaces;
   - perform task/state transitions;
   - test bounded assemblies/retrieval;
   - compare model/API predictions with actual persisted state and event receipts;
   - where useful, let multiple frontier/free model organs independently consume the same UCM2 state and preserve ancestry so agreement is not mistaken for independent evidence.

7. **Falsification phase**
   - execute negative controls, replay, crash/recovery, stale-state, conflicting alternatives, invalid transition, graph-authority and isolation tests where relevant;
   - use free APIs/models to generate adversarial or counterfactual probes when helpful;
   - preserve failures rather than optimizing them away from the report.

8. **Experience fusion**
   - record worker/API/model experiences in UCM2 with observation -> prediction -> outcome -> lesson -> claim class;
   - distinguish provider suggestion from measured machine outcome;
   - fuse compatible findings;
   - preserve contradictions/open Hyperpositions rather than forcing premature collapse.

9. **Analysis and next mutation**
   - compare hypotheses against measurements;
   - compare API-assisted paths against local/open-source/classical baselines where material;
   - change only what evidence supports;
   - identify the next highest-information UCM experiment.

10. **Persistence / knowledge transfer**
   - write a new append-only UCM2 work report;
   - commit all code/state-contract/test/report changes;
   - include API/model/provider lessons, limits, failures and useful capability mappings in the report without secrets;
   - expose reusable bounded findings for the main ClayVerse instance;
   - never auto-promote UCM2 findings into main truth.

## Completion law

A `go` cycle is not DONE merely because code was written, an API returned successfully or a model produced an answer.

DONE requires, as applicable:

`fresh evidence -> UCM2 self-read -> hypotheses -> swarm/free-API organ use -> build -> ClayVerse-use -> tests/falsification -> experience records -> analysis -> versioned work report -> committed repo state`

If a physical/VPS/API step is unavailable, complete the strongest local/repository-backed cycle possible and record the missing proof surface explicitly.

## Optimization objective

Maximize information gain and progress toward a working Unified Clay Machine, not activity count. Prefer experiments that discriminate architecture, expose failure tails, simplify the key module, improve replay/recovery, prove that a subsystem can move from hard-coded code into fluid typed state, or reveal when a free external cognitive organ provides measurable value over local/classical baselines.
