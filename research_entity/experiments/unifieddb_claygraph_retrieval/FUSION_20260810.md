# UnifiedDB + ClayGraph Retrieval Fusion — 2026-08-10

Status: CANDIDATE / TESTING — not promoted to canonical UnifiedDB or ClayGraph.
Actor: chatgpt-secondary (OpenAI GPT-5.6 Sol), temporary Clay research worker.
Mission link: Frank v0.1 fully operational on Andreas' Ubuntu developer system.

## Question
Can a rebuildable retrieval projection over canonical UnifiedDB + derived ClayGraph improve the context that Clay/Frank-facing cognition retrieves from natural-language questions, while preserving epoch/provenance boundaries and bounded latency?

## Architecture decision
Do **not** create a second truth store. Keep the existing StateLedger / UnifiedDB query plane authoritative. Add a disposable retrieval projection bound to a coherent `(source_epoch, semantic_state_hash, graph_epoch)` and reject reads after basis drift.

Candidate retrieval path:

`NL query -> FTS5 rank candidates -> exact logical entity anchor -> query-intent classification -> bounded recursive ClayGraph walk (<=2 hops) -> evidence/freshness/hypothesis-aware rerank -> context-only receipt`

The graph contributes relevance only. It never upgrades truth or effect authority.

## Iteration history / negative results preserved
1. Initial harness bug: SQL insert-column mismatch. Fixed; failure is not evidence about retrieval quality.
2. First large run exceeded the 45 s local tool budget because the LIKE baseline scaled poorly. Re-scoped to smaller reproducible runs before scaling.
3. Naive always-expand graph (`HYBRID_V1`) achieved high Recall@5 but only ~1.3% Top-1: graph fanout without query intent destroys precision. **REFUTED as default strategy.**
4. Adaptive graph/evidence V2 reached ~67.3% Top-1 but provenance Top-1 remained 0%. Exact logical-identity anchoring repaired the ambiguity.
5. The easier benchmark then reached 100%, so it was deliberately invalidated as insufficient evidence and replaced with OOD phrase variants, 2-hop queries, explicit hypothesis queries, no-graph lesion, and shuffled-graph control.
6. Harder V3 initially reached ~80.1% because 2-hop Top-1 was 0%. Query-semantic traversal-depth and target-type selection repaired the 2-hop failure without weakening the control.

## Final local synthetic benchmark
Three seeds: `20260810`, `20260811`, `20260812`.
Per seed: 200 entity families, 1,000 documents, 800 graph edges, 1,000 natural-language queries across five classes.
Total measured queries per strategy: 3,000.

| Strategy | Top-1 | MRR | Recall@5 | nDCG@5 | Mean latency | mean p95 |
|---|---:|---:|---:|---:|---:|---:|
| LIKE current-row baseline | 47.13% | 53.83% | 60.83% | 55.65% | 1,947.4 us | 2,104.8 us |
| SQLite FTS5 `ORDER BY rank` | 40.00% | 50.12% | 60.47% | 52.82% | 713.6 us | 1,096.2 us |
| HYBRID_V3_NO_GRAPH lesion | 60.00% | 60.12% | 60.47% | 60.20% | 888.1 us | 1,278.1 us |
| **HYBRID_V3** | **100.00%** | **100.00%** | **100.00%** | **100.00%** | **1,017.9 us** | **1,542.6 us** |

HYBRID_V3 Top-1 by class: direct-current 100%, provenance 100%, explicit-hypothesis 100%, graph-1-hop 100%, graph-2-hop 100% for every tested seed.

Measured trade-off against FTS5: +60.0 percentage points Top-1 for about +304 us mean latency (~42.6% latency overhead). Against the LIKE baseline, HYBRID_V3 is both +52.87 percentage points Top-1 and ~47.7% lower mean latency.

## Causal controls
- NO_GRAPH lesion: 60% overall; both graph classes fall to 0%. This shows graph traversal is needed for the graph-query gain.
- SHUFFLED_GRAPH: REQUIRES and DEPENDS_ON targets permuted independently. Mean graph-query Top-1 = 0.83%, max seed = 1.25%. The truthful-topology advantage therefore collapses under the control instead of surviving as a lexical artifact.

## Direct candidate-runtime check
The actual `UnifiedDBClayGraphRetrievalCandidate` implementation was separately rebuilt and queried on the same three-seed family (1,000 docs / 800 edges / 1,000 queries per seed). It achieved 100% Top-1 for all five classes on all three seeds. Mean query latency across seeds after the fail-closed projection guard: 1,055.4 us; mean p95: 1,543.1 us. Eight unit tests pass, including stale basis rejection, graph lesion, and fail-closed rejection of an unverified ClayGraph projection.

## Live external knowledge fusion
Primary/current sources refreshed after the first build/measure iterations:

1. SQLite FTS5 — https://www.sqlite.org/fts5.html
   - The hidden `rank` column defaults to BM25-equivalent relevance and can be faster than sorting by a direct `bm25()` call, especially with LIMIT/early abandonment. V3 changed the lexical stage to `ORDER BY rank`.
2. SQLite recursive CTE — https://www.sqlite.org/lang_with.html
   - Recursive CTEs are an official mechanism for walking trees/graphs. V3 moved bounded graph fanout into a single recursive SQL traversal rather than repeated Python edge round trips.
3. Microsoft GraphRAG local search — https://microsoft.github.io/graphrag/query/local_search/
   - Current local-search methodology uses query-related entities as graph access points, gathers connected entities/relationships and mapped text, then ranks/filters context. This independently supports the entity-anchor + graph-fanout + text-evidence shape, without making it Clay truth.
4. pgvector — https://github.com/pgvector/pgvector
   - Exact vector search preserves recall; approximate HNSW/IVFFlat trade recall for speed; hybrid Postgres FTS + vector retrieval can be combined by fusion/reranking. This is the strongest next competing retrieval family to benchmark rather than adding vectors by assumption.

## Same-run shared-state fusion
A live pre-write refresh found two new 07:00 branch tails and changed the candidate before publication:
- UnifiedDB optimized fast paths must be differential-equivalent to legacy semantics across filters, truncation, Unicode keys and fallback cases before promotion.
- ClayGraph fast-head projections must refuse verified status when same-epoch ambiguity exists or fast/legacy views diverge; version logs/graph epochs remain truth.

The candidate therefore now refuses `rebuild()` unless both `semantic_projection_verified` and `graph_projection_verified` are explicit true. This is a fail-closed input guard, not a truth minting mechanism.

## Strongest counterhypotheses / limitations
1. **Synthetic exact-ID advantage.** Many benchmark questions contain exact logical IDs. Real user language may use aliases, pronouns, misspellings, or descriptions. Entity resolution may dominate production accuracy.
2. **A database engine is not a retrieval policy.** A schema-aware SQL query compiled with exact intent can traverse joins/recursive CTEs perfectly and often faster. The measured claim is about a natural-language context-assembly workload, not universal DB superiority.
3. **Baseline coverage is incomplete.** No production Postgres FTS+pgvector, graph DB, cross-encoder reranker, or large embedding model has yet been run under matched budgets.
4. **Scale is small.** 1,000 documents per seed is proof-of-mechanism, not production-scale latency evidence.
5. **Local container != Hostinger != Andreas target.** These measurements do not satisfy Ubuntu target-hardware release evidence.
6. **Graph correctness is assumed in truthful runs.** Real ClayGraph can contain stale, conflicting or missing edges; next tests must inject those states explicitly.

## Architecture delta
Status: `SUPPORTED_CANDIDATE`, not `PROMOTED`.

Admit the following as a testable retrieval layer direction:
- canonical semantic writes remain exclusively in UnifiedDB/StateLedger;
- retrieval index and neighbor cache are disposable/rebuildable;
- every query carries coherent source/graph basis and becomes stale on epoch/hash drift;
- projector build is refused unless semantic fast/legacy equivalence and unambiguous ClayGraph projection verification are supplied;
- lexical retrieval uses FTS5 rank;
- graph expansion is conditional on relation intent;
- graph walk is bounded and recursive in SQL;
- evidence/freshness/hypothesis signals affect relevance but never truth/authority;
- graph contribution must remain lesionable and shuffled-control-sensitive;
- query receipts expose candidate counts, strategy, basis and latency.

Rollback: delete/rebuild the projection and return to the existing typed UnifiedDB query plane; no canonical state migration is required.
