## Question

What is the smallest fail-closed mechanism that separates internal event-stream integrity from external lineage admission without turning a descendant branch into canonical truth merely because it shares an admitted prefix?

## Competing realities

### H1 — one externally trusted checkpoint can close exact recovery

If UCM2 first verifies the event stream internally, then requires an externally supplied checkpoint containing root, sequence, epoch and event hash, an internally coherent sibling that diverges before that checkpoint should be rejected.

### C1 — prefix anchoring silently authorizes descendants

A naive `contains trusted hash somewhere` rule may reject old siblings but still let any descendant fork after the checkpoint masquerade as the canonical successor.

### H2 — separate exact recovery from successor candidacy

`RECOVER_EXACT` should admit only the exact externally anchored terminal head. `EXTEND_FROM_ANCHOR` may prove ancestry, but any extension must remain `CANDIDATE_SUCCESSOR` until a trusted external authority advances the anchor generation.

### C2 — the anchor can authorize itself

If the candidate event stream can issue or rewrite its own trusted anchor, a coherent sibling can simply bless itself. In that world the new gate adds no identity authority.

## Build mutation

Added `runtime/lineage_anchor.py` as an isolated UCM2 candidate. It introduces:

- immutable `LineageAnchor` with `anchor_id`, `root_module`, `seq`, `epoch`, `event_hash`, and external `authority_generation`;
- `RECOVER_EXACT`: fail closed unless the stream's terminal event is exactly the externally anchored head;
- `EXTEND_FROM_ANCHOR`: prove admitted ancestry but classify a longer descendant as `CANDIDATE_SUCCESSOR`, never newly canonical;
- explicit root/seq/epoch/hash mismatch failures;
- a verifier callback so internal event integrity is checked before lineage admission rather than being conflated with it.

The anchor object is deliberately not stored or authorized by the candidate stream in this prototype. Its provenance/authentication remains an external obligation.

## Falsification / negative controls

### Known coherent sibling regression

The UCM2-000004 sibling-rehash mechanism was reproduced as an ordinary regression, not a new unusual experiment. The sibling remains internally hash-valid but fails against the trusted baseline anchor with `LINEAGE_ANCHOR_HASH_MISMATCH`.

### Descendant ambiguity

A stream extending the trusted prefix is accepted only as `CANDIDATE_SUCCESSOR` in `EXTEND_FROM_ANCHOR` mode and is rejected by `RECOVER_EXACT` with `LINEAGE_EXACT_HEAD_REQUIRED`.

After an external authority explicitly advances the checkpoint generation to the new terminal hash, exact recovery passes.

### Rollback/truncation

A stream ending before the current external anchor fails closed with `LINEAGE_ANCHOR_NOT_PRESENT`.

### Critical preserved counterevidence

A forged/self-issued anchor built from the coherent sibling causes that sibling to pass exact recovery. This is expected and decisive: the anchor is useful only if its issuance, persistence and rollback protection are outside the candidate lineage being judged.

## Reusable bounded finding

For any future main-instance recovery design, distinguish at least:

`event integrity -> anchored ancestry -> successor candidacy -> externally admitted head`.

Collapsing those states into one `hash valid = canonical` predicate recreates the sibling/transplanted-state failure class.
