## Concurrent evidence and repair

A GitHub 409 occurred during durable writes because the repository head advanced concurrently. The write was not forced.

The new head contained a separate ClayCode loop-runtime run, `claycode-20260809T1648p0700-loop-runtime`, with three directly relevant results:

1. generic recurrence/control + existing typed semantics was sufficient for the tested loop family;
2. in-place cross-loop reads over a set-like coupled family became schedule-order dependent, while same-epoch snapshot semantics preserved permutation equivalence;

The third result contradicted the first version of this run's controller, which had treated all exhausted budgets as an ordinary halt branch. This run therefore changed the tested representation before final commit:

- dynamics classification became independent of halt/resource reason;
- budget exhaustion became an explicit `halt_reason`;
- high residual pressure at exhaustion now produces `ESCALATE`;
- low residual exhaustion may halt without claiming convergence.

This repair did not require a new ClayCode core primitive.

The concurrent scheduler-order negative result is **not re-authored as this run's own experiment**. It remains owned by its original run and is carried here as current evidence and a required next production check.

## ClayGraph finding

No ClayGraph schema change is justified.

ClayGraph V2 already preserves:

- hyperrelation identity;
- typed roles and optional ordinals;
- source/graph epochs;
- projection receipts;
- selection receipts;
- receiver delivered/reconstructed/used/effect/outcome/re-entry receipts;
- invalidation state.

A loop topology/readout can therefore be projected as derived epoch-bound graph state without giving graph activation/topology truth or effect authority.

The concurrent scheduler-order result increases the importance of carrying explicit epoch/snapshot identity for coupled loop projections.

## UnifiedDB finding

No UnifiedDB physical consolidation change is justified.

UnifiedDB V9 already separates:

- resource/capability observations;
- revisioned work specs;
- scheduler receipts;
- leases;
- execution receipts;
- local operational truth.

Loop dynamics, recurrence budget, halt reason, intervention proposal and eventual execution receipt can therefore be persisted as separate semantic/state/receipt dimensions without requiring a monolithic physical database.

The controller's `ESCALATE` or `REOPEN_ALTERNATIVE` result is a decision/proposal state, not an execution receipt.
