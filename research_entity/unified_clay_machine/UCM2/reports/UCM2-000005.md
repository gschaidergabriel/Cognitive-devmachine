## Question

Can a minimal witness outside the mutable UCM2 SQLite event database distinguish an admitted current lineage from both a valid older whole-database snapshot and a coherent same-epoch sibling history, while failing closed when the witness is absent or stale?

## Competing realities

### H1 — external-to-event-DB witness closes the tested lineage ambiguity

Bind `UCM2_CORE` identity + UCM2 schema + admitted epoch + admitted terminal event hash in a sidecar outside the SQLite event database. On restart, require exact agreement before admitting the database for automatic recovery.

Predictions:
- current admitted DB + witness -> PASS;
- older but internally valid DB + newer surviving witness -> reject;
- same-epoch internally valid sibling DB + canonical witness -> reject;
- missing witness on nonzero DB -> reject;
- DB ahead of witness -> reject instead of silently minting a new admitted generation.

### C1 — the sidecar is redundant because event hashes already suffice

If true, replacing the DB with a coherent older or sibling event history should still be uniquely decidable by the event stream itself.

This counter-reality was already weakened by UCM2-000004 and is directly discriminated here at restart/admission.

### C2 — same-host sidecar is sufficient rollback authority in all worlds

This is intentionally NOT claimed. A host/filesystem snapshot or attacker that rewrites/rolls back both SQLite and the sidecar together can preserve mutual consistency. The candidate is only independent of the mutable event database, not an independently durable or hardware-attested root of trust.

## Exactly one bounded unusual experiment

### `WHOLE_DB_TIME_TRAVEL`

At epoch 2, the test creates a consistent SQLite snapshot using SQLite's online backup API rather than copying a live WAL-mode database file. The admitted machine is then advanced to epoch 4, which advances the surviving sidecar witness. After close, only `UCM2.sqlite` is replaced by the valid epoch-2 snapshot while the newer witness remains.

Predicted H1 result: restart rejects the older but structurally valid DB because `db_epoch < anchor_epoch`.

Measured result on the self-hosted Linux runner:

`UCM2_WHOLE_DB_TIME_TRAVEL_REJECTED`

with the expected `LINEAGE_ROLLBACK_DETECTED` assertion.

Official SQLite evidence consulted:
- `https://sqlite.org/backup.html` — online backup produces a consistent destination snapshot;
- `https://sqlite.org/wal.html` — in WAL mode the WAL is part of persistent database state and must not be casually separated from the DB file.

This keeps the experiment about UCM lineage rollback rather than accidentally manufacturing a malformed WAL copy.

## Reusable bounded finding for main ClayVerse

Recovery should distinguish at least three separate questions:

1. Is this event history internally replay-complete and intact?
2. Is this exact lineage/head admitted by an independent-enough witness?
3. Is the resulting state authorized for a consequential Clay effect?

A PASS at (1) does not imply (2), and PASS at (2) does not imply (3). This also preserves the project invariant that storage quorum/reachability is not cognitive/module health or Clay authority.
