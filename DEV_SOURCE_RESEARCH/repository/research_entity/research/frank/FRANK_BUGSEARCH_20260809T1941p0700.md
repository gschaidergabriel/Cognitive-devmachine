## Confirmed / high-confidence defects

### FB-01 — V13 migration is outside canonical schema truth gates (P1)

`runtime/state/apply_current_schema.py` applies `UNIFIEDDB_V13_BUG_RESEARCH_FEEDBACK.sql`, but `runtime/state/repo_truth_gate.py`, `runtime/state/APPLIED_SCHEMA_MANIFEST_REQUIRED`, and `runtime/state/repo_semantic_materializer_impl.py` still define/check UnifiedDB 12.0 and do not require the V13 dialogue/bug-report tables. Therefore repo/materialization preflight can report a valid v12 state while exact `bug` fails at `open_unified()` because V13 is absent.

Falsifier: demonstrate a current canonical truth gate that fails closed when any of `dialogue_pending_inputs`, `dialogue_last_pairs`, `research_bug_reports` or the bug trigger contract is absent.

### FB-02 — stable bug_id is paired with mutable payload/hash (P1)

`capture_pair()` derives `bug_id` from session/cycle plus redacted pair hashes, but includes capture-time `captured_at` and current repo head in the payload before hashing. Re-capturing the same pair therefore keeps `bug_id` while payload bytes/hash can change. This contradicts the V13 completion contract `idempotent:true`. Existing test asserts same bug_id/count only and does not assert immutable payload/hash.

Falsifier: two captures of the identical source pair at different times/heads produce byte-identical package/hash or are represented as distinct immutable capture revisions.

### FB-03 — Clay duplicate handling can hide same-ID/different-hash divergence (P1)

Clay `ingest_frank_bug_feedback.py` verifies an incoming payload hash, then returns `DUPLICATE` solely on existing `bug_id`; it does not compare the stored payload hash. Combined with FB-02, Frank can publish a changed same-ID payload while Clay retains the prior one without surfacing a conflict.

Falsifier: ingest of same bug_id with a different valid payload hash is rejected/flagged as an explicit identity conflict.

### FB-04 — export is visible before Frank DB commit (P1)

`capture_pair()` writes `exports/clay_pull/bugs/<bug>.json` before `BEGIN IMMEDIATE` and the `research_bug_reports` commit. A DB failure can leave a valid-looking export with no committed Frank report; the Clay watcher can ingest it independently.

Falsifier: injected DB failure cannot leave a consumable export without a matching durable Frank-side state/receipt.

### FB-05 — exact `bug` is not globally reserved in session-skill generation (P1)

V13 inserts `bug` into `skills`/`skill_triggers`, but `runtime/skills/frank_session_skill_impl.py::RESERVED` omits `bug`. A pre-V13 skill can therefore occupy the unique `bug` trigger. Applying V13 can then skip the skill INSERT because of trigger uniqueness and subsequently fail the FK-bound `skill_revisions` insert, or otherwise collide with the protocol-reserved command.

Falsifier: migration from a valid v12 DB containing a custom `bug` trigger succeeds deterministically with explicit conflict resolution and the exact bug protocol remains authoritative.

### FB-06 — new bug-feedback tests are not executed by the current CI workflow (P1)

`.github/workflows/frank-deep-integrity.yml` compiles `tests/` but does not run pytest or `tests/test_bug_research_feedback.py`. Therefore the new tests can remain green-looking source files without execution in the advertised deep integrity gate.

Falsifier: current main workflow job shows execution of the bug-feedback regressions and fails on an intentionally broken assertion.

### FB-07 — Harness executables remain outside the deep static/compile boundary (P1)

The CI compile step covers `runtime .claude/hooks tests`, and `tests/repo_static_integrity_audit.py` scans runtime plus hooks, not `harness/`. The current `harness/frank_harness_runtime.py` therefore escaped the prior invariant that normal canonical state opens neither create nor migrate databases.

Falsifier: current CI scans/compiles Harness Python and rejects direct canonical DB creation/migration outside the explicit installer/migrator path.

### FB-08 — legacy Harness normal open creates/migrates central state and only through V7 (P1)

`harness/frank_harness_runtime.py::open_state()` creates the state directory/SQLite files through ordinary `sqlite3.connect()` and executes only schema/V6/V7 migration scripts. This conflicts with the current explicit-migration/central-state contract in `apply_current_schema.py` and can materialize stale partial canonical state if executed against a missing/outdated state directory.

Falsifier: invoking every non-test Harness entrypoint against missing canonical DBs fails closed without creating/migrating state.

### FB-09 — last-pair persistence failure is silently swallowed by Stop hook (P2)

`.claude/hooks/frank_stop_guard.py` catches every exception from `remember_output()` and discards it. A user-visible Frank reply can therefore complete while the immediately preceding pair required by exact `bug` was not persisted, causing later `BUG_CAPTURE_DEGRADED` with no contemporaneous observability.

Falsifier: injected pair-persistence failure creates an explicit diagnostic/receipt and cannot be silently reported as fully healthy.

### FB-10 — secret scrubber is materially incomplete for a durable research export (P2/security)

The Frank bug exporter currently recognizes a narrow label pattern plus `sk-*` and GitHub token forms. Common credential shapes such as bearer authorization values, private-key blocks, credential-bearing DB URLs and additional provider token families are not covered. Because the report is persisted to DB and a repository-local export surface, this is an avoidable secret-duplication risk.

Falsifier: a broad negative credential corpus proves every project-supported secret type is removed before both DB and export persistence, ideally by a shared canonical scrubber rather than a bespoke regex list.

### FB-11 — session identity is truncated in bug/Stop hooks (P2)

`frank_bug_prompt.py` and `frank_stop_guard.py` truncate `session_id` to 12 characters while other Frank runtime paths use the full session identifier. This creates an unnecessary namespace collision risk and inconsistent cross-hook identity.

Falsifier: full-session identity (or a collision-resistant digest of it) is used consistently across prompt, pair, cycle and bug-report state.

### FB-12 — Clay watcher repeatedly re-emits persistent invalid/rejected files (P2)

The Clay `--watch` loop rescans all JSON files and filters only `DUPLICATE` from its `fresh` output. A permanent `INVALID` or `REJECTED_HASH` package remains printable every polling interval, creating repeated log noise and O(N) rescans.

Falsifier: invalid/rejected path+content-hash state is checkpointed/quarantined and is emitted once per content revision.
