Status: **OWNER EXECUTION PRIORITY FOR EVERY `go` UNTIL SUPERSEDED**  
Date: 2026-08-24  
Product identity: **EntityOS**  
Integrated cognition/compute architecture: **HCU**  
Implementation codename: **Xeno**

This directive changes the optimization target of `go`: architecture synthesis is not the primary output. `go` converges on the first finished runnable Xeno with a specialized ~0.8B cognitive core and complete harness, then keeps recursively improving the accepted Xeno until a newer explicit owner instruction supersedes this directive.

There is no terminal `done forever` state. Xeno v1 is the first accepted baseline. Xeno remains an implementation codename inside EntityOS/HCU; it does not create a second truth authority, effect authority, product identity or persistent entity.

## Phase B — recursive improvement after Xeno v1

When a bound `XENO_V1_ACCEPTANCE/v1` PASS exists, each later `go` executes:

`measure accepted Xeno -> select highest-information implementation delta -> patch -> positive/negative/recovery tests -> benchmark frozen vector -> deterministic compare -> promote or reject/rework -> update baseline -> repeat`

This continues until a newer explicit owner instruction changes the objective.

## Recursive objective

Recursion improves the whole Xeno system rather than one vanity metric. Protected dimensions include capability/task quality, latency, throughput, RSS, recovery, authority correctness, token efficiency, ClayCode share, engine swap, two-slot harness, prestage, GRID10, peer link, dashboard correctness and Global J-Space causal gain.

Token count, logical-worker count, consensus, architecture elegance, benchmark cherry-picking or a single improved scalar never constitutes recursive progress.

## Promotion law — anti-Goodhart v2

Deterministic comparison gate: `tools/xeno_build_gate.py` / `XENO_PROMOTION_GATE/v2`.

The gate uses an **epsilon-Pareto + cross-group** rule rather than requiring every metric to improve on every patch:

- every protected metric must be present and finite;
- material regression on any protected metric rejects the candidate;
- deterministic correctness-style recovery/authority/harness pass rates are hard no-regression fences, including tiny negative movement;
- practical-significance floors prevent benchmark jitter or microscopic deltas from minting progress;
- a normal candidate must improve at least **two independent metric groups** among Capability/Quality, Efficiency, Architecture/Cognition and Robustness/Authority;
- at least one improved group must be a core group: Capability/Quality, Efficiency or Architecture/Cognition;
- a ClayCode migration additionally requires meaningful `claycode_fraction` progress, but unrelated protected dimensions may remain stable;
- a single composite metric or model self-report cannot self-promote a candidate;
- benchmark/composite inputs must come from bound executable receipts with reproducible measurement definitions.

This preserves the long-horizon requirement that the whole metric vector improves over successive accepted cycles without creating an impossible per-patch requirement that encourages metric gaming or rejects useful orthogonal improvements.

### Progress groups

- `capability_quality`: `capability_pass_rate`, `task_quality_score`
- `efficiency`: `p50_latency_ms`, `p95_latency_ms`, `throughput_tokens_s`, `rss_mb`, `token_efficiency_score`
- `architecture_cognition`: `claycode_fraction`, `grid10_pass_rate`, `jspace_causal_gain_score`
- `robustness_authority`: recovery, authority-boundary, engine-swap, two-slot, prestage, peer-link and dashboard pass rates

Global J-Space is a standing protected objective. It need not improve on every unrelated patch, but material regression rejects the candidate and J-Space-focused patches must use model-specific causal evidence rather than coherence/self-report.
