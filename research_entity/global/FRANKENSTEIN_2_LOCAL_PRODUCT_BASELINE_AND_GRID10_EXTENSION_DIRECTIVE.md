# FRANKENSTEIN 2.0 — LOCAL PRODUCT BASELINE + GRID10 EXTENSION BINDING

Status: Triggerword-4 binding/addendum
Scope: product-location and degradation semantics only

## 1. Purpose

This file closes the explicit addendum reference from `TRIGGERWORD_4_GRID10_COGNITIVE_RUNTIME_DIRECTIVE.md`.
It does not create a second product, state authority, effect path, or runtime-credit mechanism.

## 2. Product baseline

The Frankenstein 2.0 baseline product is the local host harness (`frankenstein_harness`).
The baseline startup surface is:

```bash
bash scripts/run.sh
```

A first useful local startup must not require VPS access, GRID10 availability, network access, or a model/provider connection.
Missing optional external surfaces must degrade capability rather than invalidate the baseline product.

## 3. GRID10 / HCU extension

GRID10/HCU is an attached cognition/compute organ reached through the `GRID10Plugin` boundary.
It extends the local product; it does not replace the local product or become a competing product authority.

The current GRID startup chain remains:

`GRIDKernel -> ResearchEntityRuntime -> VisualCortex -> UnifiedDBBridge -> VoiceCortex -> FrankensteinGRIDSystem`

If GRID10 is absent or fails during startup, the host core remains authoritative and continues in a degraded/core-only mode where the current implementation supports that path.

## 4. VPS role

The owner-provisioned VPS may serve as remote embodiment, validation, worker, or compute substrate when current higher authority admits it.
It is not the Frankenstein 2.0 product authority and is not required to define the local baseline product.

Execution rights, billing/provider restrictions, and runtime-credit rules are resolved from the newest admitted owner/supervisor authority; this addendum does not hard-code an older supervisor epoch.

## 5. State, cognition, and effects

Canonical durable state/evidence authority remains deterministic under the current admitted architecture.
GRID/HCU/model/provider outputs remain candidate cognition unless promoted through the currently admitted deterministic boundaries.
No model/provider output may mint world fact, completion, or real-effect authority by itself.

## 6. Evidence boundary

Source presence or successful local/component tests do not establish VPS, physical GRID10, GWT/J-Space, effect, completion, training, or whole-system runtime credit.
Runtime claims require exact observed receipts at the claimed source/artifact/environment scope.

## 7. Triggerword-4 interpretation

For Triggerword 4, continue from the newest verified checkpoint rather than rebuilding the product around the VPS.
Use the local host harness as baseline, attach GRID10/HCU through the plugin boundary, and treat remote/VPS execution as an extension or validation surface subject to current authority.

This binding is intentionally narrow. Any later explicit owner/supervisor authority or successor directive outranks it.
