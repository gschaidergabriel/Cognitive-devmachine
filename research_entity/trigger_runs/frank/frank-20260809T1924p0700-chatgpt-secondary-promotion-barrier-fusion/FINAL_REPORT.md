## 2. New cross-branch mechanism candidate

The newest ordinary-code H1 work introduces a cognitive snapshot -> fresh commit revalidation barrier for external effects. It records the Assembly identity, dependency versions and capability epoch at snapshot time, then rejects or re-routes commit when a relevant dependency or capability epoch changed. Unrelated state changes need not abort the action.

This mechanism should be generalized as a **Semantic Promotion Barrier** candidate for any transition where a derived/candidate state is about to become durable or causally privileged after being evaluated against an earlier snapshot.

Candidate form:

`candidate derived from snapshot S`
`-> evaluate/test under S`
`-> identify exact relevant dependencies D + semantic/version identities`
`-> immediately before promotion/commit, re-read current versions D'`
`-> unchanged relevant dependencies: eligible for the domain-specific deterministic gateway`
`-> changed relevant dependency: reject/re-evaluate`
`-> dependency absent from original snapshot: reassemble/re-evaluate`

The barrier itself grants no execution authority and does not establish truth. It only prevents stale evaluation state from silently crossing a durable promotion/commit boundary.

## 3. Why this matters beyond external effects

### Adaptive visual learner

FRANK 0.1 requires shadow evaluation, atomic promotion, feature-backbone compatibility and last-known-good rollback for the Micro Visual Classifier. A classifier candidate can pass shadow evaluation and still be stale at promotion time if the visual feature backbone/export version, calibration set, trusted-example lineage or active user/workspace context changed between evaluation and promotion.

Candidate dependency set for MVC promotion:

- feature-backbone model/export/quantization identity;
- training example lineage hashes and GOLD/SILVER admission state;
- calibration/open-set evaluation corpus identity;
- currently promoted classifier/prototype version;
- user/workspace semantic epoch where relevant;
- resource-policy version when promotion changes runtime duty cycle.

The promotion barrier therefore creates a direct executable test for the Qwen3.5 shared-vision hypothesis: changing the 4B/vision export or quantization between MVC shadow evaluation and promotion must invalidate/re-evaluate the candidate rather than silently keeping old familiarity prototypes as if their feature space were unchanged.

### Durable topology / memory coupling

A proposed slow ClayGraph/Hyperposition binding or memory promotion may have been justified by provenance/context evidence that becomes stale before durable publication. The same barrier can require the exact ancestry/context/version evidence used by the candidate to remain current at publication time. This prevents correlated re-entry or late-arriving counterevidence from being ignored merely because a promotion job was already queued.

This does not promote the richer reversal-aware binding lattice. It supplies a generic stale-evidence guard that both the simple baseline and richer candidates can share.

### Peer backflow / verified semantic writeback

Peer results are proposals/evidence, not authority. If a strong peer returns against semantic epoch E but relevant local state advances before writeback, the result should either re-expand/revalidate against the current Assembly or be stored as provenance-bound historical evidence rather than blindly overwrite current local state.

Again the barrier does not decide whether the peer is correct; it prevents temporal laundering of stale reasoning into current state.

## 4. Hypothesis and counterhypothesis

**H-FRANK-R10-PROMOTION-BARRIER — OPEN:** one typed fresh-commit/promotion primitive parameterized by relevant dependency identities can reduce stale effect execution, stale MVC promotion, stale topology/memory promotion and stale peer writeback while allowing unrelated concurrent state changes to proceed.

**Counterhypothesis:** domain-specific validation is simpler and safer; forcing all promotion domains through one generic barrier creates dependency bookkeeping overhead, false invalidations or hidden coupling.

**Falsifier:** matched H1 traces show that a generic barrier either misses a stale-promotion class caught by domain-specific logic, causes materially worse abort/retry/tail-latency rates, or cannot express the relevant version/provenance dependencies without domain escape hatches.

## 5. Required discriminator family

Add an H1 cross-domain barrier fixture family with common semantics and domain-specific dependency sets:

1. effect intent: relevant target/policy changes reject; unrelated state change does not;
2. MVC candidate: feature-backbone/version/calibration change between shadow evaluation and promotion forces re-evaluation; unrelated memory event does not;
3. topology/memory candidate: provenance/context/version/counterevidence changes force re-evaluation;
4. peer writeback: relevant local semantic epoch/dependency change forces reassembly or historical-only storage;
5. ABA case: A -> B -> A must remain detectably changed through version/generation identity;
6. crash/restart: pending candidate cannot promote after restart without revalidating current dependencies;
7. adversarial dependency laundering: a dependency first introduced at commit time forces reassembly instead of being silently accepted.

Metrics: stale-promotion false-accept rate, false-invalidation rate, retry/reassembly rate, p50/p95/p99 barrier overhead, dependency-set size, replay determinism, recovery behavior and domain-specific outcome quality.
