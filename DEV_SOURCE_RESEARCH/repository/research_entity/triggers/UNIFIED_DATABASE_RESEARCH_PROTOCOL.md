# UnifiedDB Research Trigger Protocol

Trigger: `unifieddb`

## Purpose

Run the dedicated RAE scientific programme for the Unified Database / Unified Cognitive Data Substrate concept defined in `research_entity/global/UNIFIED_DATABASE_RESEARCH_FOUNDATION.md`.

The research target is a logically unified Clay-native persistence, identity, query, transaction and retrieval substrate spanning FRANK's exact state/event history, temporal/provenance data, relational/graph memory, vector/tensor semantics, activation/assemblies, GWT-facing state and effect/outcome/re-entry records, while retaining measured physical isolation where warranted.

This protocol does **not** assume that all storage engines should physically merge.

## Mandatory boot and mesh

Follow `MASTER_RESEARCH_TRIGGER_PROTOCOL.md` and `INTERCONNECTED_RESEARCH_MESH_PROTOCOL.md`.

Before Fusion 1, materialize `INTERCONNECT_MANIFEST.json` covering every registered scientific branch. UnifiedDB is a peer scientific branch and must both consume and write back to the complete mesh.

Priority for this branch:

`clay -> frank -> claycode -> claygraph -> hyperposition -> gwt -> emergenz -> unifieddb history`

Deep inputs are mandatory from:
- FRANK current architecture/runtime and live/twin constraints;
- ClayCode current semantic/query/effect contracts;
- ClayGraph current graph/memory/database-migration research;
- Hyperposition current epoch/topology/firebreak research.

## Required research loop

1. Inventory current FRANK/RAE stores, state classes, indexes, derived views and authority boundaries.
2. Classify each store/object as authoritative, derived/rebuildable, external/isolated, cache, index, activation/salience, model state or effect/outcome state.
3. Build at least four comparison architectures where feasible: specialized baseline, logically unified API, shared canonical store + sidecars, and physical consolidation candidate.
4. Generate falsifiable hypotheses and counterhypotheses around consistency, performance, recovery, migration, selection integrity and common-mode risk.
5. Execute external research using current provider policy for database systems, MVCC/snapshots, multimodel/polystore systems, graph/vector/FTS integration, event sourcing, local-first/edge persistence, recovery and security/capability boundaries.
6. Execute feasible code/simulation/benchmark experiments. Synthetic results remain synthetic until target replication.
7. Test query/result equivalence and replay under concurrent updates, crash/restart, compaction/rebuild and derived-index lag.
8. Test selection provenance/integrity independently from record provenance.
9. Measure whether physical consolidation actually reduces IPC/serialization/cache cost enough to justify increased contention/crash radius/write amplification.
10. Produce a reversible migration/rollback plan and explicit `KEEP_ISOLATED` decisions where appropriate.
11. Feed results to every materially affected branch, with explicit feedback to FRANK, ClayCode and ClayGraph.

## Mandatory evaluation dimensions

- semantic correctness and type preservation;
- exact replay and snapshot consistency;
- temporal/provenance correctness;
- query-result equivalence;
- graph/vector/FTS retrieval quality;
- selection integrity;
- transaction/effect atomicity;
- p50/p95/p99 latency;
- write/read amplification;
- memory/storage footprint;
- concurrency/lock/contention behavior;
- crash recovery and rebuild time;
- migration/rollback safety;
- IPC/serialization savings;
- common-mode failure radius;
- Android/edge energy/thermal impact where relevant;
- model-facing token/context cost where relevant.

## Hard scientific boundaries

- Unified semantics do not imply unified physical storage.
- Graph activation, embeddings and retrieval rank are not truth or authority.
- A faster architecture that loses invariants, provenance, replay or selection integrity fails.
- A physically unified database that increases common-mode failure or recovery risk may be rejected even if median latency improves.
- No branch agreement counts as independent replication when it shares the same experiment/source ancestry.
- Database integration or cognitive integration is not evidence of phenomenal consciousness.

## Promotion discipline

Strong promotion requires target-relevant evidence, reversible migration, regression/replay success, crash/recovery evidence and independent validation of high-impact correctness claims. Until then candidates remain OPEN/HOLD.
