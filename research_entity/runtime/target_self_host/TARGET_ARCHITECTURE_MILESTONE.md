## GWT / observability / re-entry
The runtime keeps the required causal stages distinct:

`competition -> ignition -> addressability -> delivery -> reconstruction -> uptake -> causal use -> outcome -> re-entry`

A DB guard rejects receiver use without delivery + reconstruction + uptake. Measurement receipts are bound to state/graph epoch, estimator and result hash. A measurement is forbidden from minting truth/authority.

`EmergenceReadout` is vector-valued. Missing counterfactual measurements remain the literal state `UNKNOWN`, never implicit zero.

Counterfactual `InterventionSpec` and `ReplayReceipt` surfaces exist, including frozen-model-output identity, matched control and rollback recipe.

## Emergence and loop-regime boundary
State inadequacy produces `ABSTAIN_STATE_INADEQUATE`.

Novelty, recurrence, synergy or graph density alone cannot promote an emergence claim. Functional-pattern support requires receiver use + truthful re-entry + lesion/rescue + shuffle + OOD + macro/control shadows. It is never a phenomenal-consciousness claim.

The loop controller also exposes `UNDERCOUPLED`, `ADAPTIVE` and `OVERCOUPLED_TRIPWIRE`. Permanent ignition/synchrony, dimensional collapse or hub collapse is treated as a failure regime, not as a target to maximize.

Control-policy updates are only staged after matched-intervention causal credit, OOD PASS and an explicit rollback recipe.
