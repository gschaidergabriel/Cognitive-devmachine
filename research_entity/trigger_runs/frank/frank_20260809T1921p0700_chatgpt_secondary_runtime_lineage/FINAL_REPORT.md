## 4. Fusion 1 contradiction map

Earlier ClayCode effect-recovery work showed two crash worlds can leave the same local prepared state while the remote effect differs. Fixed RETRY duplicates one world; fixed ABSTAIN loses the other. It proposed stable `effect_operation_id`, semantic fingerprint, delivery/recovery class and `UNCERTAIN`.

The selected runtime 0.3 is stronger on authority but its inspected public semantics remain `validated opaque capability -> adapter function -> PASS/FAULT trace`, without visible stable external operation identity/recovery class/UNCERTAIN contract. This is not proof every adapter is unsafe; it is a carry-forward gap between durable negative knowledge and a newer current candidate.

### C2 — freshness does not solve recovery

Fresh relevant-dependency/capability revalidation before authority handoff is necessary but cannot tell whether an external sink changed if the crash happens after dispatch. Therefore freshness and outcome certainty are independent dimensions.

### C3 — local atomicity cannot be overgeneralized

SQLite can provide crash-atomic transactions inside its own storage domain. That does not make an arbitrary external API/process/device effect atomic with a separate local receipt.

### C4 — exactly-once is scope-dependent

Kafka's strong exactly-once paths rely on integrated idempotence/transactions and coordinated Kafka state. FRANK therefore needs explicit recovery/delivery scope per adapter/effect domain rather than a universal `COMMITTED == exactly once` interpretation.

### C5 — multi-worker evolution creates lineage risk

Git preserves old results, but preservation does not prove a replacement candidate still satisfies them. This motivates an executable Negative-Result Lineage Gate hypothesis.

## 5. External research synthesis

Official SQLite atomic-commit documentation supports crash-atomicity for effects kept inside one transactional storage domain; it does not cover arbitrary external sinks.

Official Apache Kafka documentation ties stronger exactly-once behavior to idempotent/transactional coordination and, for Kafka Streams, integrated input/output/state-store semantics rather than arbitrary external side effects.

`Machine-Checked Dual-Write Recovery from a Committed Log` (arXiv:2608.00501, 2026) provides a current formal-preprint information-bound result: post-crash local state can be identical while external sink acceptance differs; sink evidence/fencing changes what recovery can know. This is preprint evidence, not FRANK validation.

The HTTPAPI Idempotency-Key draft provides a useful request-identity/fingerprint analogue, but the inspected draft is expired and is context-only, not a current RFC.

NIST software-assurance material supports traceable/verifiable requirements and historical automated testing as assurance practices; this supports the engineering motivation for lineage tests but does not validate the FRANK-specific gate design.
