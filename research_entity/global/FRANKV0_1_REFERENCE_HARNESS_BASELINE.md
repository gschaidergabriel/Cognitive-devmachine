# FRANK v0.1 REFERENCE HARNESS BASELINE

Status: PROJECT_OWNER_FIXED_DIRECTIVE
Date: 2026-08-09
Scope: H1 Reference Harness, H2 Clay Harness, H3 One-Module/Binary FRANK and Research-Entity runtime parity work

## 1. Fixed baseline — current target architecture in normal code

H1 is **not** a reconstruction of the old `frankv0.1` architecture as the target implementation.

H1 is the executable reference implementation of the **current evidence-supported FRANK target architecture**, implemented first in ordinary host code (for example Python/Rust/normal runtime libraries) so architecture research, integration, replay, ablation, recovery and performance work can proceed before ClayCode is release-complete.

Reference law:

`H1_REFERENCE_HARNESS := CURRENT_FRANK_TARGET_ARCHITECTURE implemented in normal host code`

`H2_CLAY_HARNESS := ClayCode-native reimplementation of the same frozen H1 semantics`

`H3_ONE_MODULE_FRANK := consolidated one-module/binary realization preserving the proven H1/H2 semantics`

The current target architecture is derived from owner-fixed contracts plus the newest admissible whole-mesh evidence. It includes the current final-binary direction, loop-of-loops/GWT, UnifiedDB/derived topology, independent peer cognition/backflow, Digital Retina/adaptive visual learning, Needle boundary, effect/authority separation, recovery and all other current target mechanisms.

The Research Entity itself does NOT become Frank. It remains `frank-project-global-research-entity`; ChatGPT, Claude Code and other workers remain temporary research actors of that Research Entity.

## 2. ClayCode gate does not idle H1 research/build work

The formal program release order remains:

`BASE ClayCode PASS -> H1 PASS -> H2 PASS -> H3 PASS`.

But this is a **promotion/gate order**, not a prohibition on useful upstream-parallel implementation.

While BASE ClayCode is unfinished, Frank/Harness workers MAY and SHOULD build, test and refine the new target architecture in ordinary host code whenever the work is independent of unavailable ClayCode execution.

Therefore:

`H1 stage blocked on BASE for PASS != H1 implementation forbidden before BASE PASS`.

Allowed before BASE PASS includes:

- target architecture modules/state machines in ordinary code;
- canonical event/state/effect/outcome ledger;
- UnifiedDB logical semantics and derived topology;
- GWT stages and recurrence controllers;
- peer-instance/backflow/capability fabric;
- Digital Retina and adaptive visual learner mechanics;
- Needle boundary fixtures/adapters;
- effect/authority/resource gates;
- replay, ablation, fuzz, recovery and long-horizon tests;
- diagnostic ClayGraph/run-graph exports;
- target-shaped model ABI fixtures;
- semantic traces and Golden Traces to become the H2 differential oracle.

H1 may accumulate real completion receipts during BASE. However H1 release/PASS remains gated until BASE ClayCode passes and the H1 release audit confirms the frozen reference semantics against the current target contracts.

## 3. Role of historical `frankv0.1`

The repository `gschaidergabriel/frankv0.1` remains an important **evidence, regression and archaeology source**, not the architecture template that H1 must preserve wholesale.

Its behavior is classified as:

- `REUSABLE_MECHANISM` — a mechanism still supported by current target research;
- `REGRESSION_ORACLE` — a historical success/failure that defines a test;
- `LIVE_USER_EVIDENCE` — current Andreas-use evidence relevant to general architecture;
- `COMPATIBILITY_REQUIREMENT` — behavior that the new target must preserve for a justified product/user reason;
- `SUPERSEDED_ARCHITECTURE` — old implementation structure not carried forward;
- `OPEN_COMPARISON` — historical mechanism retained only as an experimental baseline.

Historical code must not silently drag obsolete service/module boundaries into the new H1 architecture.

## 4. H1 is the executable specification of the new architecture

H1 exists so the new architecture can be made concrete before ClayCode is complete.

Every architecture mechanism intended for H2/H3 should, where feasible, become observable executable H1 semantics with:

- typed state and stable semantic identities;
- explicit transitions and causal parentage;
- deterministic fixtures where external/model nondeterminism would hide architecture mechanics;
- provenance and evidence class;
- authority/effect boundaries;
- snapshots/recovery/replay;
- lesion/intervention points;
- runtime/resource measurements;
- Golden Traces and expected state deltas.

Architecture prose alone is not the H1 oracle. Executed H1 behavior plus frozen contracts/receipts is.

## 5. Freeze-and-transfer law

The migration from normal code to ClayCode must not be a redesign pass.

Once an H1 subsystem is sufficiently tested, freeze its semantic contract and trace corpus. H2 then implements that same behavior in ClayCode.

For each transferred subsystem:

`normal-code H1 state/input/intervention`
`-> expected semantic trace/outcome`

must commute with:

`ClayCode H2 state/input/intervention`
`-> normalized semantic trace/outcome`.

A difference is classified as one of:

- `H2_IMPLEMENTATION_BUG`;
- `H1_REFERENCE_BUG`;
- `AMBIGUOUS_CONTRACT`;
- `CLAYCODE_EXPRESSIBILITY_GAP`;
- `INTENTIONAL_VERSIONED_DIVERGENCE`.

If ClayCode cannot express the validated H1 semantics, reopen the ClayCode gate rather than simplifying the architecture to fit the language.

## 6. Why this parallel path is preferred

The normal-code-first path is preferred when it increases information gain because it:

1. prevents Frank workers from idling while ClayCode BASE closes;
2. lets architecture failures be discovered without confounding them with an immature compiler/runtime;
3. creates a high-quality executable oracle for ClayCode;
4. separates `architecture defect` from `language/compiler defect`;
5. allows web research, experiments and peer-worker findings to alter the current H1 architecture before the ClayCode freeze;
6. gives H2 a concrete differential target rather than prose reconstruction;
7. makes later H3 consolidation measurable against two implementations of the same semantics.

The cost is duplicate implementation effort. That cost is acceptable only if H1 remains deliberately clear/reference-oriented and H2 reuses the frozen semantic contracts/tests rather than re-researching the architecture.

## 8. General product, Andreas-informed adaptation

The Harness remains a general FRANK architecture. Andreas is the longitudinal founding/pilot user, not hard-coded product logic.

Adaptation rule:

`repeated Andreas use pattern -> measured need/failure/opportunity -> generalized capability hypothesis -> test across representative scenarios -> promote as configurable/default product behavior only if evidence supports general value`.

Person-specific preferences belong in user state/profile layers and must not be confused with universal architecture invariants.
