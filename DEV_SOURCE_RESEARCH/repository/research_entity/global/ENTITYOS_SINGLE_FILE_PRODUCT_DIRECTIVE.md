# ENTITYOS SINGLE-FILE PRODUCT DIRECTIVE

## Authority

Owner-fixed product boundary, 2026-08-16. This directive is additive to the active `CLAYVERSE_CLAY_MACHINE_ONLY` engineering program and supersedes any older release wording that requires the delivered Clay Machine itself to be a directory, bundle, launcher plus sidecars, or daemon set.

## Research endpoint clarity

**The endpoint of the research is EntityOS itself: the single-file Clay Computer.**

`Clay Machine` names the internal computer architecture being developed and progressively embodied inside EntityOS. It is **not** a separate final research endpoint, separate release, or open-ended successor product.

All research programs, work packages, architecture studies, ClayCode/compiler/VM work, Linux interop, networking, process/terminal, data, visual/video, audio, security, recovery, Vercel tooling, tests, receipts and development branches are means for converging on the exact delivered `EntityOS` artifact.

Canonical short form:

`ENTITYOS = SINGLE-FILE CLAY COMPUTER`

Whenever wording elsewhere says that work targets or completes the “Clay Machine”, its final product interpretation is the one executable EntityOS Clay Computer unless a newer explicit owner directive supersedes this law.

## Product law

The delivered Clay Machine is exactly **one executable file named `EntityOS`**.

Development source, tests, build tooling and research artifacts may remain modular. The accepted release/runtime package must collapse the admitted ClayCode compiler/toolchain, Clay VM, Clay runtime/environment, minimal ClayOS services and controlled Linux interoperability into the single `EntityOS` executable.

A development directory, container image, installer, launcher plus sidecars, separate compiler/runtime tree or service set is not the final product unless the accepted delivery still resolves to one runnable `EntityOS` file.

Runtime-generated user state is data, not an installation sidecar. Persistent state may be stored through explicit single-file-compatible/XDG-style state interfaces when required for continuity, but the user must not need a multi-file installation contract to launch EntityOS.

A frozen launcher or one-file packaging mechanism does not by itself establish EntityOS acceptance. The exact artifact must actually carry and execute the admitted canonical ClayCode -> compiler/executable IR -> Clay VM -> Clay Environment/ClayOS path and the accepted typed capability boundaries. Packaging a host-language harness into one file does not silently become the Clay Computer.

## Zero-install reconciliation

The existing Clay Machine zero-install/copy-and-run requirement remains active, but its final release interpretation is stronger: copying the single `EntityOS` executable to a compatible supported Ubuntu/Linux target must be sufficient to launch the product without package-manager installation, root setup, hidden developer checkout or mandatory companion runtime files.

Host kernel/ABI/device requirements must be declared and measured; Linux remains host substrate, not Clay semantic authority.

## First-start permission continuity

At the first normal user-facing launch, EntityOS must perform one explicit initial approval action for the internal application/runtime permission set intended by the product. Accepted approval is persisted so subsequent starts do not repeatedly ask for the same internal approval.

This one-time internal approval does **not** bypass Linux/host security, external provider authorization, consequential effect gates, provenance checks, fail-closed policy or owner authority. Host-level prompts that the OS/provider requires remain outside EntityOS control.

Until a graphical one-click surface is accepted, backend/state mechanisms may be implemented and tested independently, but they must not be reported as final one-click UX PASS.

## Acceptance extension

Whole Clay Machine / EntityOS acceptance additionally requires that the exact tested artifact:

1. is one executable named `EntityOS`;
2. launches from a clean compatible Ubuntu/Linux environment without mandatory installation or companion runtime files;
3. carries the admitted canonical ClayCode -> executable IR -> Clay VM -> ClayOS path;
4. satisfies the active network, terminal/process, data, visual/video, audio, state/recovery and Linux-interop gates at their accepted scopes;
5. survives copy/move/restart/crash tests required by the active contracts;
6. preserves provenance/build identity and fail-closed behavior;
7. implements persistent first-start internal approval continuity without weakening host/effect authority.

Component PASS, source-tree success, an extracted build directory, a Python-only development launch, a historical artifact on a different head, or a provider deployment state does not imply EntityOS release PASS.

## `go`

Exact `go` converges on this research/product endpoint. Each complete macro-cycle must either build/update/test the exact one-file `EntityOS` artifact or name the exact blocker and next executable sandbox step required to make that artifact stronger/buildable. Exactly one bounded unusual experiment remains required per user-triggered macro-cycle.

A `go` cycle should not stop at the first green component result when another safe, authorized, high-information step toward the exact EntityOS artifact remains executable in the current turn.
