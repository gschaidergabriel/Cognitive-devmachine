## Findings

### F1 — WP02 should retain strict LALR as a hard grammar-construction gate

Lark documents that ordinary LALR may resolve shift/reduce conflicts automatically, while `strict=True` raises on shift/reduce and regex collisions. Regex collision detection in strict mode requires the interegular integration and is limited by regex feature support. Lark also documents the contextual lexer as a parser-state-informed way to narrow legal terminals.

Implication:
- keep strict LALR construction as a mandatory negative gate;
- keep an explicit collision corpus and deterministic failing fixtures;
- do not treat successful ordinary LALR construction as sufficient evidence;
- retain a full-corpus parser gate after construction;
- canonical IR/hash determinism remains a separate downstream acceptance property and must not be inferred from parser determinism.

This strengthens the current WP02 closure plan; it does not force new ClayCode surface syntax.

### F2 — WIT is suitable as a typed lowering/interop contract, not as ClayCode semantics

The Component Model documentation defines WIT as an interface/world contract language and explicitly not as a general-purpose language that defines behavior. Therefore WIT can serve as a backend-facing typed ABI/adapter description for a WASM Component Model lowering, but it must not become the semantic source of truth or replace ClayCode IR/effect semantics.

Implication:
- ClayCode canonical IR/type-effect remains authoritative;
- a WIT world/interface can be generated from admitted typed FFI/effect contracts where WASM/WASI is selected as an Ubuntu backend;
- translation validation must bind ClayCode semantic/effect hashes to generated WIT/component artifacts and observed execution receipts.

No core-language redesign is warranted from this source.

### F3 — Component Model resources are a strong implementation candidate for non-forgeable host resource identity

The Component Model and Wasmtime documentation define resources as handle-like references to entities outside a component; Wasmtime states that the guest cannot forge the resource representation and tracks own/borrow use dynamically. Resource types are distinct across instantiations and host-defined resource types can be kept type-distinct.

Implication for WP07:
- if a WASM Component Model backend is used, map ClayCode host-resource capabilities to host-owned typed resources rather than serializable bearer descriptions;
- preserve ClayCode/FRANK's stronger authority rule: possession of an admitted host resource handle is necessary but not automatically sufficient for every effect; policy/revocation/epoch checks remain in the external effect gateway;
- never serialize a resource's descriptive representation and later treat it as restored execution authority;
- test stale/revoked handles, cross-instance type confusion, borrow-after-return, ownership transfer and replay/restart invalidation.

This independently supports the current architecture constraint `descriptive capability != execution authority` and WP07's opaque/sealed host-handle direction. It is backend support, not proof that WASM is the final or only backend.

## Counterhypotheses / falsifiers

CH1: Strict LALR may reject a grammar feature that is necessary for the frozen semantics. Falsifier/decision test: produce a minimal executable source fixture required by the frozen semantic corpus that cannot be expressed without an unavoidable strict-LALR collision; only then consider grammar restructuring or parser-engine change.

CH2: WIT/Component Model resources may impose unacceptable latency, platform/toolchain friction or missing host functionality for the Ubuntu FRANK target. Falsifier/decision test: differential microbenchmark and fault/restart test against a native typed-FFI backend using the same ClayCode effect/resource fixtures.

CH3: Component Model non-forgeability may still be insufficient for FRANK authority semantics because revocation, policy epoch and external authorization are host concerns. This is expected rather than contradictory. Test: structural/serialized forgery must fail, and revoked/stale handles must fail even when the underlying resource identity remains valid.
