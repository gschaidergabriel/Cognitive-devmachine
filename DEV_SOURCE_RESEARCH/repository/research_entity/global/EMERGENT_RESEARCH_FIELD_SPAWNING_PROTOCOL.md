# Emergent Research Field Spawning Protocol

**Status:** PROJECT_OWNER_FIXED POST-L0 `666` BEHAVIOR
**Applies to:** exact trigger `666` after `666_RELEASE_GATE = PASS`

## 0. Core idea

After Level 0 archive assimilation is complete, `666` does not directly route every worker into the obvious next implementation milestone.

Instead each `666` invocation spawns one temporary research field with a distinct, partly stochastic lens. Every field shares the complete FRANK Research Center narrative, current evidence base, historical archive knowledge and current milestone as a common attractor, but explores a different local path.

Goal:

`shared narrative + diverse local lenses + cross-field coupling + evidence-preserving fusion -> emergent global search quality`

The current milestone is a North Star, not a command that every field must work on directly.

## 1. Level-0 exception

While `666_RELEASE_GATE != PASS`:

`666 -> Level 0 archive assimilation only`

After Level 0 PASS:

`666 -> spawn new field -> research -> cross-connect -> feed mesh`

## 2. Field identity and persistence

Every spawned field receives:

- unique `field_id`;
- human-readable generated name;
- `spawn_seed`;
- creation timestamp;
- spawning run id;
- shared program milestone at spawn time;
- local research lens;
- required source branches to connect;
- hypotheses and counterhypotheses;
- falsifier/completion test;
- active worker/lease state;
- findings and negative results;
- cross-room feedback;
- lifecycle state.

Canonical registry:

`research_entity/emergent_fields/FIELD_REGISTRY.json`

Field state:

`research_entity/emergent_fields/fields/<field_id>/FIELD_STATE.json`

## 3. Stochastic but not arbitrary

The field generator uses a recorded random seed so the spawn decision is reproducible.

Randomness supplies diversity; relevance filters prevent nonsense.

Candidate lens families include, and may expand beyond:

- dynamical systems;
- control theory;
- information theory;
- category/relational structures;
- topology/geometry;
- distributed systems;
- programming-language semantics;
- databases/transaction theory;
- compiler/runtime design;
- neuroscience/cognitive architectures;
- evolutionary/ecological systems;
- cybernetics/homeostasis;
- security/adversarial systems;
- fault tolerance/recovery;
- causal inference;
- compression/representation learning;
- game theory/multi-agent coordination;
- physics-inspired fields/phase transitions;
- artistic/visual/narrative composition translated into falsifiable engineering mechanisms;
- philosophy of mind translated into operational distinctions;
- measurement/metrology;
- human-computer interaction;
- novel cross-domain combinations generated from two or more lens families.

A candidate field is rejected and re-sampled if it is merely a renamed duplicate of a recently spawned field or has no plausible connection to the FRANK program.

## 4. Diversity pressure

Selection should maximize:

`field_value = novelty + orthogonality + cross_branch_connectivity + falsifiability + expected_information_gain + possible_milestone_relevance - duplication - ancestry_echo - vague_metaphor_penalty`

The selection is stochastic among high-value candidates rather than always choosing the top deterministic score.

This deliberately prevents every worker from converging immediately on ClayCode/Harness implementation.

## 5. Shared narrative constraint

Every field receives the same global context:

- current `PROGRAM_STATE.json`;
- shared Research Center narrative;
- completed Level-0 archive knowledge;
- current branch packets/deltas;
- negative-result/failure history;
- current milestone and gates;
- GWT/Hyperposition measurement contracts;
- Harness/ClayGraph/UnifiedDB/ClayCode/FRANK current state.

The field then asks:

> From this unusual lens, what mechanism, contradiction, measurement, representation or experiment could materially change what the research organism currently believes or builds?

## 6. Required cross-connection

A spawned field may not remain isolated.

Before completion it must connect to at least two existing research branches or previously spawned fields where relevant and publish at least one of:

- supported mechanism;
- counterhypothesis;
- architecture implication;
- measurement proposal;
- executable experiment;
- negative result;
- historical connection;
- explicit `NO_CHANGE` after a discriminating test.

Cross-field agreement does not count as independent replication if it shares the same source ancestry.

## 7. Field roles

The existing tAvern roles remain usable inside a field:

- CARTOGRAPHER;
- FORGE;
- ABYSS;
- REPLICATOR;
- SYNTHESIZER;
- CHEF;
- SOLO_RESEARCHER.

The field itself is not a new permanent scientific branch unless repeated evidence demonstrates that it deserves promotion.

## 8. Lifecycle

Default field lifecycle:

`SPAWNED -> ACTIVE -> CROSS_CONNECTED -> TESTED -> INTEGRATED -> CLOSED`

Possible alternative terminal states:

- `REFUTED`;
- `NO_CHANGE`;
- `MERGED_INTO_EXISTING_BRANCH`;
- `PROMOTED_TO_PERSISTENT_BRANCH`;
- `BLOCKED`.

Promotion to a permanent trigger/branch requires explicit durable evidence or owner instruction; repeated random spawning alone is not enough.

## 9. Milestone relationship

Milestones remain sequential release gates:

`Level 0 -> ClayCode BASE -> H1 -> H2 -> H3 -> UnifiedDB -> Training Data -> WAIT`

But after Level 0, `666` does not automatically perform the next milestone's obvious work.

Instead fields create diverse knowledge pressure around the whole system. Material findings are routed to the specialist room that owns the affected gate artifact. Those specialist branches may then build/test the milestone through their own triggers, existing workers and cross-room handoffs.

Therefore:

`milestone = global attractor`

`666 field = exploratory perturbation`

`specialist rooms = implementation/validation sinks`

`fusion = global integration`

## 10. Emergence measurement

The research center should measure whether stochastic field spawning actually helps.

Track at least:

- novel hypotheses per field;
- fraction surviving counterargument;
- cross-branch connections discovered;
- independent evidence introduced;
- negative results found;
- gate-relevant findings;
- implementation changes caused;
- duplicate/echo rate;
- time/token cost;
- field-to-field diversity;
- long-term contribution to milestone closure.

Compare against deterministic direct-dispatch baselines when feasible.

If stochastic spawning produces mostly noise or duplicate work, tune the diversity/relevance sampler rather than preserving randomness dogmatically.

## 11. Safety / epistemic rule

Random field generation may create bold hypotheses, not truth.

Every promoted result still requires normal evidence, provenance, counterhypothesis and falsification discipline.

## 12. Compact law

Before Level 0 PASS:

`666 = exhaustive archive assimilation`

After Level 0 PASS:

`666 = seeded stochastic research-field genesis + immediate research + network feedback`
